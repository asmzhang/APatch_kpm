# wxshadow P0：地址空间验证（2026-11-02）

「都要防」这个口径定下来之后，wxshadow 从「暂不立项」转为立项，先做 P0——不碰页表，只验证
后面所有工作依赖的两件事实。本文只记 P0，P1 起另开记录。

## 1. 要验证什么

wxshadow 的全部动作都落在「另一个进程的某一页」上，所以必须先能稳定做到：

1. 从 pid 找到目标 `mm`，再从 `mm->pgd` 走到目标 `va` 的 leaf PTE；
2. 把 PTE 里的物理地址换算成**内核可读**的地址，读到与目标进程完全相同的内容。

第 2 条在 KPM 里不是白给的：`linear_voffset`、`memstart_addr`、`page_shift`、`pgd_va` 这些
KernelPatch 全局**一个都没有 `KP_EXPORT_SYMBOL`**，LKM 兼容表里也没有，所以模块里既不能写
`phys_to_virt()`，也不能读 `page_shift`。探针改成现场量（见 `Developer/tools/wxshadow-probe/README.md`）。

## 2. 第一次上机就把 Pixel 6 打掉了（PAN）

`load rc=0`、`init done`、自校验通过，但第一条 `ctl wxs_probe self` 直接触发 panic。
pstore（`/sys/fs/pstore/console-ramoops-0`）里的原文：

```
[+] KP I wxs_probe: selfcheck=1 linear_voffset=0xffffff7f80000000 va_bits=39
[+] KP I wxs_probe: init done
[+] KP I load_module_ex: [wxs_probe] succeed with [(null)]
[+] KP I module_control0: name wxs_probe, args: self
Unable to handle kernel access to user memory outside uaccess routines at virtual address 0000007fd439e094
pc : 0xffffffe4318039b4
==== Start KernelPatch for Kernel panic ====
Kernel panic - not syncing: Oops: Fatal exception
Reboot reason: 0xbaba - Kernel PANIC
```

原因在探针自己：ctl0 回写时写了 `out_msg[len] = 0;`。`out_msg` 是用户地址，内核直接给用户地址赋值
在开了 PAN 的 arm64 上是致命错误（不是普通缺页，是 "outside uaccess routines"）。
改成只走 `compat_copy_to_user(out_msg, buf, len + 1)`（NUL 一起拷）之后正常。

教训写进探针 README：**ctl0 的回写通道只有 `compat_copy_to_user` 一条，任何 `out_msg[i] = ...` 都是 panic。**
这台机器是仓库里唯一能做 KPM 真机的 6.1 设备，所以这次重启也提醒：新模块第一次上机先只读、先只调
`self` 这种不碰目标的命令，再逐步加压。

## 3. 结果（两台，同一份 9432 B 产物）

| 设备 | 形态 / 管理器 uid | 换算因子 | 探针结果 |
| --- | --- | --- | --- |
| Pixel 6（`22251FDF60004E`，6.1.99-android14） | kernel / 10273 | `va_bits=39`、`linear_voffset=0xffffff7f80000000`、`page_offset=0xffffff8000000000`、`pgd_off=56` | `pid=6074 va=0x7abc7d1100 pgd=0xffffff8859625000 pte=0xa80009f9715f43 pa=0x9f9715100 kva=0xffffff8979715100 data=4f524947494e414c2d30313233343536` |
| 小米 13（`3e6f1443`，5.10.149-android12-9，`kernelpatch-lkm`） | lkm / 10270 | `va_bits=39`、`linear_voffset=0xffffff7f80000000`、`page_offset=0xffffff8000000000`、`pgd_off=72` | `pid=26162 va=0x7ceb711100 pgd=0xffffff88e6a12000 pte=0xa80008e8561f43 pa=0x8e8561100 kva=0xffffff8868561100 data=4f524947494e414c2d30313233343536` |

`data=` 那一串是 `ORIGINAL-0123456`，与客户端自己读出来的 16 字节逐字节相同 —— 内核侧读到的就是目标进程看到的那一页。

两个附带结论：

- `mm_struct_offset.pgd_offset` 两台机器不同（6.1 = 56，5.10 = 72），必须用 KP 解析出来的值；
  这也解释了为什么上游 wxshadow 一定要走 `mm_struct_offset` 而不是硬编码。
- `va_bits=39` 意味着 `PAGE_OFFSET = 0xffffff8000000000`，所以内核侧地址都落在 `0xffffff80_xxxxxxxx` 之上；
  一开始按 `~0 << (va_bits - 1)` 算出来的 `0xffffffc000000000` 是错的，正确公式是 `~0 << va_bits`。

## 4. 产物与符号面

- `Developer/tools/wxshadow-probe/wxs_probe_0.0.1.kpm` 9432 B（不入库，源码入库）；
- `python tools/load_forms.py --artifact … --kallsyms local/mi13_kallsyms.txt` → `und=10 形态=kernel,lkm kernel缺=0 lkm缺=0`；
- 依赖符号：`find_task_by_vpid`、`get_task_mm`、`mmput`、`__kmalloc`、`kfree`（两台都有），
  KP 侧 `pgtable_entry` + `mm_struct_offset`（两形态都在兼容表里）。
  注意 `set_pte_at`、`flush_tlb_page`、`page_address`、`alloc_pages` 这些**不是**两台都有的符号，
  P1 若需要改页表得自己内联 TLBI，不能指望这些名字。

## 5. 下一步（P1 判据）

P1 = 双视图：把目标页克隆到一张 shadow 页、改 PTE 指向它，要求

- 目标进程读同一 `va` 读到 shadow 页的内容；
- `release` 之后逐字节复原、PTE 回到原值；
- 全程 `dmesg` 无 warning，`unload` 后无残留页。

同时要先把 `set_pte_at` / TLB 这两条路在 5.10 上补齐（该内核没有 `set_pte_at` 符号，只有 `__flush_tlb_range`）。
