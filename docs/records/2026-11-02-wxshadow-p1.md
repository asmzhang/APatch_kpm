# wxshadow P1：双视图（PTE 切到影子页）

日期：2026-11-02。对象：`Developer/tools/wxshadow-probe/`（探针，不是成品模块）。
前置：P0 已验证「pid → leaf PTE → 物理地址 → 内核可读」这条路（见 [2026-11-02-wxshadow-p0.md](2026-11-02-wxshadow-p0.md)）。

## 1. 这一步要证明什么

P0 只证明「能看见目标进程的页」。P1 要证明「能让目标进程看见另一份内容，并且退得回去」：

1. 把目标进程某一页 4 KiB 匿名页的 PTE 指向我们自己分配的一页（影子页），影子页里保留原内容但改了几个字节；
2. 目标进程读同一个虚拟地址，读到的是影子页的内容；
3. `release` 后 PTE 回到原值，目标进程读回原内容，影子页释放；
4. 全过程 dmesg 无 BUG / Oops / 锁告警，`unload` 不留残留。

## 2. 实现（`wxs_probe.c` 0.0.2）

状态机：`none(0) → attached(1) → installed(2)`，`attach` 时 `get_task_mm()` 持有 mm 引用，`detach`/`exit` 时 `mmput`。

- `attach <pid> <va>`：`find_task_by_vpid` → `get_task_mm` → `pgd = *(mm + mm_struct_offset.pgd_offset)` → `pgtable_entry(pgd, va)`；要求 `PTE_VALID` 且 `(pte & PTE_TYPE_MASK) == PTE_TYPE_PAGE`（只收 4 KiB leaf），记下原 PTE 与 `va & 0xfff`。
- `install <hexbytes>`：`__kmalloc(4096)` 并要求页对齐 → 从原物理页整页复制 → 在页内偏移处写新内容 → `dc cvau` 逐行清到 PoC → `at s1e1w` 取影子页物理地址 → 新 PTE = 原 PTE 属性位保留、只换 `[47:12]` 输出地址 → 写 PTE → `dsb ishst` → TLBI → `dsb ish`/`isb`。
- `release`：确认当前 PTE 仍是我们装的那一个（不是就不动，报 `pte changed`），写回原 PTE，同样 TLBI，`kfree` 影子页。
- TLB：用 `VAAE1IS`（by VA、All ASID、EL1、inner shareable）。目标 mm 可能同时在别的核上跑，按 ASID 精确刷反而会漏，所以整 ASID 一起刷。VA 编码与内核 `__TLBI_VADDR` 一致（`va>>12` 取低 44 位）。

| 小米 13 `sha256:cdc3e9167b02`（5.10.149-android12-9，`kernelpatch-lkm`） | lkm / 10270 | `rc=0` | `rc=0` | `534841444f572d7031…` | 内容回 `4f524947494e414c…` |

- 两台 `load rc=0` / `unload rc=0`，dmesg 无 BUG、无 Oops、无 `__list_del_entry_valid`。
- 判据全部达成：目标进程读到影子内容、模块侧 `probe` 读到同一页同一份内容、`release` 后逐字节复原且 PTE 回原值、卸载无残留（`wxs_detach()` 兜底）。

## 4. 两个踩坑

1. **页内偏移丢失**：`attach` 里把 `wxs_tva` 直接掩成页基址，`install` 又用 `wxs_tva & 0xfff` 算偏移 → 恒为 0，补丁写在了页首而客户端读的是 `+0x100`，于是「PTE 换了、内容没变」。修法：单独存 `wxs_toff = va & 0xfff`。教训：PTE 级切换成功不代表数据改动生效，判据必须落在「目标进程读到什么」。
2. **客户端没重编**：`make clean` 会删掉 `wxs_client`，只跑 `make all` 就把旧二进制推上去了，导致日志文件根本没生成。修法：`make client` 单独目标，脚本里先 `ls -l` 确认时间戳。

## 5. 已知限制（P2 再处理）

- 只处理 4 KiB leaf；huge/block/table 一律拒绝（与上游一致，上游还要再拆 huge PMD）。
- **没有取 `mmap_lock`**：KP 没有导出 `mm_struct` 的 `mmap_lock` 偏移，探针只在「目标页不被 munmap/mremap」的前提下工作；客户端是单线程只读，够用，但这不是可交付形态。P2 要么补偏移推导，要么按上游那样做 mm 级准入门。
- 只做**数据视图**：影子页与原页同样是可读写，没有 UXN/执行视图，也没有 icache 同步（P2 的 UXN fault 与 `STEPPING` 态才需要）。
- 没有 generation/token，多个客户端同时 attach 会互相覆盖（单实例状态机）。

## 7. P2a：执行视图（2026-11-02 加）

P1 只证明「数据视图能换」。P2a 要把同一套换页用到**取指**上：影子页里放一条改过的指令，
目标进程执行同一个 va，跑的是影子页里的代码。

- 客户端 `wxs_exec_client.c`：在一页 `rwx` 匿名内存的 `+0x100` 写 `mov w0, #1; ret`（`0x52800020`、`0xd65f03c0`），
  自己 `__builtin___clear_cache` 之后每 500 ms 调一次，把返回值写日志。
- 模块侧在 `install` 里除了 `dc cvau` 清数据缓存，再加 `ic ialluis` + `dsb ish` + `isb`：
  I-cache 按 VA+ASID 维护，目标进程在别的 ASID 上，按 VA 刷不到它，只能整域刷。
- 装的内容是 `mov w0, #2; ret`（`40008052c0035fd6`）。

| 设备 | 形态 | install 前 | install 后 | release 后 |
| --- | --- | --- | --- | --- |
| Pixel 6 `sha256:433ab88276ec`（6.1.99） | kernel / 10273 | `ret=1` | `ret=2` | `ret=1` |
| 小米 13 `sha256:cdc3e9167b02`（5.10.149，LKM） | lkm / 10270 | `ret=1` | `ret=2` | `ret=1` |

两台都是 `load rc=0` / `unload rc=0`，dmesg 无 BUG / Oops。

**这一步还不是双视图。** 现在目标进程读和取指都落在影子页上（一个视图）。
真正的「读原字节、执行改过的字节」需要两个视图：

1. 影子页设成**执行专用**（arm64 上就是去掉 `PTE_USER`、清 `UXN`，`AP=00` 让 EL0 没有数据访问权，只能取指）；
2. 原页设成**只读不可执行**（`UXN=1`，`AP` 保持 EL0 可读）；
3. EL0 取指 → 影子页；EL0 读 → 权限异常 → 在异常里切回原页读完，下一次取指再切回影子页。

这需要钩 `do_mem_abort`（或 `do_page_fault`）并区分 IABT/DABT，是 P2b 的内容；
先做一步只读探针（钩上、只打印目标 va 的 ESR，不改状态），确认两形态都能钩住、ESR 与预期一致，再加状态机。

## 6. 下一步（P2）

按 [2026-11-02-wxshadow-feasibility.md](2026-11-02-wxshadow-feasibility.md) §7 的判据：

1. 用 **UXN fault**（源 PTE 置 UXN → 执行时 IABT）代替显式 `install` 触发，处理程序里切到影子页；
2. 加执行视图：`BRK` 单步（ABI 已在 P0 探针验过）跑被替换的指令再切回；
3. 生命周期：in-flight 收拾、`exit_mmap`/`copy_process` 钩子、卸载时确保没有线程停在影子页上；
4. 再做一次「App 自查」演示：目标进程读自己的代码段，看到的是原字节。

## 8. P2b 第一步：钩住 do_mem_abort，只记录不改状态（2026-11-02）

判据：两形态都能 `hook_wrap2(do_mem_abort, ...)` 成功；目标页产生缺页时能看到 ESR/FAR；记录本身对进程透明（进程照常收到 SIGSEGV 并能在 handler 里恢复）。

实现（`wxs_probe.c`，`arm` / `disarm` / `faults` 三个新命令）：

- `wxs_do_mem_abort = kallsyms_lookup_name("do_mem_abort")`，找不到只 `logkw` 不报错（P0/P1 不需要它）。
- `hook_wrap2(wxs_do_mem_abort, wxs_mem_abort_before, 0, 0)`；回调签名 `void (hook_fargs2_t *args, void *udata)`，`arg0=far`、`arg1=esr`、`arg2=struct pt_regs *`。
- 回调只处理 `[wxs_tva, wxs_tva+4096)` 的地址，前 8 条打 `far/esr/ec/fsc/pc`，不修改任何 PTE，也不动 `skip_origin`。
- `wxs_detach()` 里先 `hook_unwrap` 再放状态，避免 attach 到另一进程时旧钩子挂着。

客户端加了「可控缺页」：第 6 个 tick（3 秒）对自身页 `mprotect(PROT_NONE)`，读一次（`sigsetjmp`/`siglongjmp` + SIGSEGV handler 兜住），再恢复 `PROT_READ|WRITE|EXEC`。

结果（同一份 21112 B 产物，`und=10` 两形态 0 缺失）：

| 设备 | 形态 | dmesg | 客户端 |
| --- | --- | --- | --- |
| Pixel 6（6.1.99-android14） | kernel / 10273 | `fault far=0x782a8f4100 esr=0x92000007 ec=0x24 fsc=0x7 pc=0x221fec` | `fault-probe: caught signal, hit=1` |
| 小米 13（5.10.149-android12-9） | lkm / 10270 | `fault far=0x79d5617100 esr=0x92000007 ec=0x24 fsc=0x7 pc=0x221fec` | `fault-probe: caught signal, hit=1` |

ESR 解读（两机完全一致）：`EC=0x24` 是「来自更低异常级的数据异常」（`0x25` 才是同级的），说明缺页确实源自 EL0；`FSC=0x07` 是「翻译错误、第 3 级」，因为 `PROT_NONE` 在 Linux 上是把 PTE 置无效而不是降权限。取指异常应是 `EC=0x20`、权限类应是 `FSC=0x0D/0x0F`——这三个值就是后面状态机的判据。

钩子透明性：客户端照常拿到 SIGSEGV、handler 跑完、程序继续（`t=6 ret=1`），系统无 BUG、`unload rc=0`。

踩坑：

- `pkill -f wxs_exec_client` 会把执行它的 `su -c` shell 一起杀掉（命令行里含同样字符串），后续命令全部不执行、且看不出报错；要用 `pkill -x wxs_exec_client`。
- `attach` 会先 `wxs_detach()`（含摘钩），所以换目标进程后必须重新 `arm`。
- 改 C 字符串时经 JSON→bash→Python 三层转义，`
` 会被吃成真换行，编译报 `missing terminating '"' character`；这次用正则 `"([^"
]*)
(")` 批量修回（`wxs_probe.c` 9 处、`wxs_exec_client.c` 2 处）。

## 9. P2b 第二步：取指异常驱动的单向切换（2026-11-02）

### 9.1 先做了一次「不处理」的对照实验（重要）

把目标页 PTE 直接置 `PTE_UXN`（`1 << 54`），不加任何处理，然后让客户端继续执行：

- `uxn ok old=0xa800092661bf43 new=0xe800092661bf43`（bit54 置位）。
- 3 秒内 `faults=29653339`（约每秒一千万次），客户端日志停在 `t=2`、进程没有前进、也没收到 SIGSEGV。
- `uxnclear` 还原 PTE 后进程立刻恢复（`t=21`、`t=22` 继续），faults 只再涨 1。

结论：**用户态取指权限异常不会被投递成信号，内核原地重试那条指令**。所以状态机必须自己把 PTE 换成可执行的影子页、并置 `skip_origin` 跳过内核默认处理；只观察不处理会把 CPU 拖进密集异常循环（这次没死机是因为马上还原了）。

### 9.2 `hold` + 钩子切换

新增 `hold` 命令：把 PTE 写回「原页 + UXN」，标记 `wxs_hold = 1`，等下一次取指异常。回调里：

- 只认 `EC == 0x20`（来自 EL0 的 IABT），且 `wxs_hold`、影子 PTE 就绪；
- `wxs_write_pte(wxs_pte_installed)`（写影子 PTE + `dsb ishst` + `tlbi vaae1is` + `dsb ish` + `isb`）；
- `args->skip_origin = 1` 让 `do_mem_abort` 不再执行，异常返回时 CPU 重试这条指令，这次取到的是影子页；
- 安全阀：同一页累计切换超过 64 次就放弃处理并 `logke`，避免影子页本身也取不到指时把设备拖死。

结果（同一份 25040 B 产物，`und=10` 两形态 0 缺失）：

| 设备 | 形态 | hold 前 | hold 后 | dmesg | 计数 |
| --- | --- | --- | --- | --- | --- |
| Pixel 6（6.1.99-android14） | kernel / 10273 | `ret=2`（已装影子页） | 仍 `ret=2`，无停顿 | `iabt switch far=0x7275a8e100 pc=0x7275a8e100 n=1` | `faults=2 sw=1 hold=0` |
| 小米 13（5.10.149-android12-9） | lkm / 10270 | `ret=2` | 仍 `ret=2`，无停顿 | `iabt switch far=0x72d626b100 pc=0x72d626b100 n=1` | `faults=2 sw=1 hold=0` |

对比 9.1 的三千万次异常：**处理了就是 1 次异常一次切换**，这就是 `skip_origin` 的意义。

`release` 后两台都回到 `pte back to 0xa800…`、客户端 `ret=1`，`disarm`+`unload rc=0` 无残留。

### 9.3 现在的局限

这一步仍然是「时间上交替」而不是「同时两个视图」：切到影子页之后，读同一页读到的也是影子内容。要做到「读原字节、执行改过的字节」，还得让影子页与源页在同一时刻具备不同权限（源页 `r--`、影子页可执行），靠 DABT/IABT 分流——那是 P2c。


## 10. P2c：双视图成立（读原字节、执行改过的字节）（2026-11-02）

### 10.1 关键实测：arm64 确实有「只可执行、不可读写」

把目标页 PTE 的用户位（`PTE_USER`，AP[1]）清掉、`UXN` 保持 0，然后让客户端继续执行：

- `xo ok pte=0xa80009758eef03`（用户位已清）；
- 之后 3 秒里 `iatb=0`、`dabt=1`：**取指一直成功**，只有那次数据读（tick 6 的探测）缺页。

也就是说：EL0 的取指只看 `UXN`，`AP[1]=0` 只切断数据访问。这条实测推翻了「取指需要读权限」的直觉判断，也说明**真双视图在 arm64 上可行**——源页 `r--`（`UXN=1`）、影子页 `--x`（清 `PTE_USER`、`UXN=0`）。

### 10.2 `dual` 命令与两条切换路径

- 影子 PTE：`(原属性 & ~PTE_UXN & ~PTE_USER) | PTE_AF`，PA 指向影子页 → 只能取指；
- 源页 PTE：`原 PTE | PTE_UXN` → 只能读；
- 初始落源页（读得到原字节）；
- 回调：`EC=0x20`（取指异常）→ 写影子 PTE；`EC=0x24`（数据异常）→ 写源页 PTE；两条都 `skip_origin=1`，异常返回重试即命中对应视图；
- 风暴保护：累计切换超过 200000 次就关掉 dual、还原源 PTE 并 `logke`。

### 10.3 结果（同一份 29432 B 产物，`und=10` 两形态 0 缺失）

| 设备 | 形态 | 执行 | 读 | 计数 |
| --- | --- | --- | --- | --- |
| Pixel 6（6.1.99-android14） | kernel / 10273 | `ret=2`（影子页里的 `mov w0,#2`） | `rd=20008052`（原页里的 `mov w0,#1`） | `iabt=6 dabt=6` |
| 小米 13（5.10.149-android12-9） | lkm / 10270 | `ret=2` | `rd=20008052` | `iabt=6 dabt=6` |

同一个 VA、同一时刻：**执行走影子页（改过的），读走原页（没改的）**。每次切换 1 次异常，没有风暴。

### 10.4 局限（P3 要解决）

- **内核会覆盖我们的 PTE**：客户端自己 `mprotect` 一次，内核就按 VMA 重写 PTE，我们的双视图被冲掉（第一次 dual 测试就是这样变成 `ret=1` 的）。成品必须接管或拦截 `mprotect`/`mmap`/`mremap` 对目标页的改动。
- **大页未处理**：只接受 4 KiB leaf；PMD 映射要先 `__split_huge_pmd`。
- **多线程同页**：两个线程一个读一个执行会互相踢，切换次数翻倍；需要按 mm 加锁或允许短暂双写。
- **fork/exit 生命周期**：`copy_process` 要复制影子页状态，`exit_mmap` 要回收影子页，当前 probe 只靠 `release` 手动收。



## 11. P2d：A/B 实验、自建 oracle，与「只读文件页」的限制

### 11.1 原本打算用 runtime-sense 当靶子

`D:/work/vmp/arsenal/defend/runtime-sense`（`com.xff.launch`）自带 `self.own_text` 自校验，看起来正合适：A 组用普通 inline patch（`wxs_probe` 的 `poke`，直接写目标进程原页）应当报 hooked，B 组用 `dual` 双视图应当报干净。

### 11.2 为什么它测不到（重要，且不是说它写错了）

它的 `checkOwnTextIntegrity()` 分两步：从磁盘读 `.so` 的 `.text`（`readFileAt(path, base_file_off + sh->sh_offset)`，`detection/src/main/cpp/detector/integrity_detector.cpp:542`，`path` 就是 `base.apk`），再用直接指针读内存逐 8 字节比。

问题在于：APK 里的 `.so` 是 **stored（不压缩）** 的，Android 直接 `mmap` APK 的这一段来加载。也就是说：

- 内存里的 `.text` 页 == page cache 里 APK 那个偏移的页
- 它第 1 步读的也是那一页

我们用内核线性映射写补丁，写的就是这一页。于是「内存 == 磁盘」，`diff == 0`，日志打 `[XFF-SELF] our own .text CLEAN`。

用 `dd if=base.apk bs=1 skip=$((0xe9b000+0x35704)) count=16 | od -An -tx1` 直接验证：补丁在位时设备读到 `5f 24 03 d5 e0 03 00 aa ...`，还原后读回 `c0 03 5f d6 1f 20 03 d5`。APK 的 `mtime` 一直是 2025-03-23，存储上没变。

**边界要说准确**：这个判据对**用户态**改法仍然有效——`ptrace` / 写 `/proc/pid/mem` / Frida 往只读私有映射里写会触发写时复制，进程拿到自己的一份私有页，文件页不变，于是内存 ≠ 磁盘，一比就能发现。失效的只是「内核直接写物理页」这一类，因为它绕过了写时复制。

结论：拿它做 A/B 靶子没有说服力（既不能证伪也不能证真），改用自建 oracle。

### 11.3 自建 oracle（`Developer/tools/wxshadow-probe/wxs_oracle.c`）

- 目标函数用全局 asm 定义，排除编译器插序言：`add w0,w0,#1` / `add w0,w0,w0` / `ret`（`0x11000400` / `0x0B000000` / `0xD65F03C0`）
- 期望值以常量数组形式**编译进代码**：`static const uint32_t oracle_ref[] = {0x11000400u, 0x0B000000u, 0xD65F03C0u};`
- 主循环每 2 秒 `memcmp((const void*)&oracle_target, oracle_ref, 12)`，打印 `t=%d state=%s ret=%u`（`CLEAN` / `PATCHED`），并真实调用一次 `oracle_target(20)`（期望 42）

这条判据不依赖磁盘，所以内核改物理页也瞒不过它。

### 11.4 A 组：普通 patch，oracle 报 PATCHED（成立）

Pixel 6（kernel 形态 / uid 10273），pid 9176，`oracle target=0x221c98`：

```
attach pid=9176 va=0x221000 off=0xc98 pte=0x2000008ac8cfc3
poke ok pid=9176 kva=0xffffff800ac8cc98 len=12
t=8 state=PATCHED ret=99
```

`poke` 写入 `60 0c 80 52 c0 03 5f d6 1f 20 03 d5`（`mov w0,#0x63; ret; nop`），oracle 立刻报 `PATCHED` 且返回值变 99。**A 组成立。**

### 11.5 B 组：`dual` 在只读文件页上没生效（未完成）

同一进程同一页：还原原字节（`poke 000400110000000bc0035fd6`）后 `CLEAN ret=42`，再 `dual 600c8052c0035fd61f2003d5`：

```
dual ok pid=9176 va=0x221000 shadow_pa=0x9a0a0b000 exec=0x200009a0a0bf83 read=0x6000008ac8cfc3
stats iabt=0 dabt=0 other=0 sw=0
t=13 state=CLEAN ret=42
release: pte changed (now 0x6000008ac8cfc3 expect 0x200009a0a0bfc3)
```

即：PTE 写进去了，但**一次缺页都没触发**，执行仍在原页（`ret=42`），且 `release` 时发现页上的 PTE 已经不是 dual 期望的那个。

与 P2c 成功案例的差别：P2c 的 `wxs_exec_client` 用的是**匿名 rwx 页**（`AP[2]=0`，可写），这次是 **ELF 文件映射的只读代码页**（`AP[2]=1`，`0x6000008ac8cfc3` 里 bit7 就是 AP[2]）。怀疑方向（未验证）：

1. 只读文件页上的 PTE 改写被内核或硬件忽略/回退
2. I-cache 里已经有原页的指令，本轮循环没有再取指，自然没有 IABT
3. TLBI 没覆盖到目标进程的 ASID，旧 TLB 条目仍在用

这三条可以用单变量实验区分：先 `ic ialluis` + 强制跳到一个新函数、再改 PTE、或先 `mprotect` 成可写再 dual。

### 11.6 结论

- 「改得动」已验证（`poke` 改到目标页、oracle 报 PATCHED、返回值变化）
- 「藏得住」只在匿名页上验证过（P2c）；**只读文件页这一关没过**，这是 P3 的第 0 件事
- runtime-sense 不能当 B 组靶子（判据对内核写物理页失效），已改用自建 oracle

### 11.7 本轮顺带补的探针能力

`wxs_probe` 新增：`detach`（释放 `mm` 引用并摘钩，解决 app 被杀后 `refused to die`）、`poke`（写目标页原页，模拟普通 inline hook）、`findnop`（找函数尾 `ret; nop` 填充）、`findpat`（按 4 字节模式搜目标进程页）。
