### 1b. MSR 宏与 DFR0 语义 —— **成立**

**寄存器名与编码**：

- `hwbp.c:256-259`：`SH_DBG_RD`→`"mrs %0, dbgb" RS #n "_el1"`、`SH_DBG_WR`→`"msr dbgb" RS #n "_el1, %0"`，RS∈{"vr","cr"}，n=0..15（:250-254）。展开为 `dbgbvr<N>_el1` / `dbgbcr<N>_el1`——与上游 v6.1 `arch/arm64/include/asm/hw_breakpoint.h` 的 `AARCH64_DBG_READ/WRITE`（`"mrs %0, dbgb" REG #N "_el1"`）逐字符同构，且全部为 EL1 变体（op1=0，EL0 变体 `dbgbvr<n>_el0` 不存在——VVR/BCR 只有 EL1 编码）。
- 上游 `arch/arm64/kernel/hw_breakpoint.c` v6.1 的 `write_wb_reg()` 即 switch 0..15 调用同一宏组并以 `isb()` 收尾——模块的 16-case 结构与其一一对应。
- 二进制验证：16 个 BVR 读 case（0x2624-0x2724，CRm=0..15, op2=4）、16 个 BCR 读 case（0x2748-0x27fc，op2=5）、写 BCR（0x2b2c-0x2bd4，op2=4）、写 BVR（0x2c44-0x2cbc，op2=5）齐全；CRm 恰为槽号，无缺槽。
- 编码语义核对（ARM ARM）：DBGBVR<n>_EL1 = op0=3?否——op0=2（Debug），按指令编码 op0 bit=1、op1=0b000、CRn=0b0000、op2=4（BVR）/5（BCR）、CRm=n，与二进制解码（op0=1 表示 o0 bit 置位的 MRS/MSR 系统寄存器指令形式）一致；EL1 变体在 EL1 可读写，模块运行于 EL1（KPM），合法。

**BRPs 字段语义**：

- `hwbp.c:289-294`：读 `ID_AA64DFR0_EL1`，`slot_count = ((dfr0>>12)&0xF)+1`，钳 16。注释（:290）明确「实现数-1」。
- 架构语义：ID_AA64DFR0_EL1.BRPs（bits[15:12]）=「断点数−1」（0b0000=1 个断点，0b1111=16 个）→ **+1 是正确方向**（原任务描述中"BRPs 字段=实现数-1"+1 与代码一致）。上游 `get_num_brps()` 实现同为 `((dfr0>>12)&0xf)+1`，且同样受 ARM_MAX_BRP=16 钳制（v6.1 中 max=16 恰好等于编码上限，钳位在 6.1 上是冗余但无害的防御）。
- Pixel 6（Cortex-X1/A78，8 硬件断点）下 slot_count=8，扫描 0..7，不越界。
- DFR0 读只在 `sh_hwbp_init()`（:803-808，模块 init 进程上下文）执行一次，异常上下文零初始化依赖。

**边界**：`SH_DBG_SLOTS` 固定 16 case，slot_count 可能小于 16，循环以 `n < total` 截断（:312、:343）——不会访问未实现槽位；单独调用 `sh_dbg_read/write_*` 的路径（仅经 rearm/disarm 循环）同样受 total 约束。**无缺陷**。

### 1c. 语义等价性 —— **成立**

- 旧三件套语义：disable（清槽使能）→ modify（改 perf 内部 addr，随后重装 BVR）→ enable（恢复使能）。
- 新实现（:312-326）：`BVR==old && BCR&1` → 写 `BCR&~1`（停用）→ 写 `BVR=dst`（改址）→ 写回**读到的原 BCR 值**（重新武装）。
- BCR 保真性：写回的是 `sh_dbg_read_bcr(n)` 读出的完整 64 位值（:318、:324），除 bit0 被 :322 临时清零外，PMC/PAC/E/BAS/HPC/SSC/LBN/BT 等全部位段原样写回——**保真**。与上游 `hw_breakpoint_control(RESTORE/INSTALL)`「写 BVR 再写 BCR=原值」的二步序实质等价（上游 RESTORE 也是整值写回 BCR）。
- 一个有意的语义增强：旧 perf 路径只改触发事件对应的那个槽；新路径一次改齐**所有** BVR 匹配的已武装槽（:315 匹配即改，moved 计数）。注释（:297-299）说明动机：同址重复 hook 时旧法另一个槽留在原地会立即再命中。该增强与三件套语义不冲突（三件套本就该对同一地址的所有武装槽生效）。
- 匹配条件 `BVR==old`（:302/:315）用 `bp_addr&~3` 归一化，与硬件断点对齐粒度一致；`dst==old` 短路（:308）避免无谓翻动。
- 匹配以「寄存器当前值」为准而非 perf 记录——即使 BVR 曾被框架改写（休眠唤醒恢复等），只要仍等于 node->bp_addr 就能被找到，比旧实现更鲁棒。

### 1d. 已知局限（perf 内部状态不同步）—— **成立，且后果评估正确（不超过错采）**

机制确认（上游 v6.1 `arch/arm64/kernel/hw_breakpoint.c`）：

- perf 内部 `arch_hw_breakpoint.info.address` 记录的是 hook 时的 `target_addr`；`hw_breakpoint_thread_switch`（切换进出禁用状态时 `toggle_bp_registers`）只翻转 BCR bit0，不写 BVR；但 `hw_breakpoint_reset`（CPU PM 恢复/热插拔，`cpu_suspend_set_dbg_restorer`）与断点迁移时走 `HW_BREAKPOINT_RESTORE`＝`write_wb_reg(BVR, info->address)`＋BCR 写回——**BVR 会被重装回旧地址**。模块注释（hwbp.c:242-246）对此的描述准确。

后果推演（关键问题：错采会不会升级为比错采更严重的事态）：

1. **不会死循环自触发**。框架 `breakpoint_handler()` 的命中判定是 `read_wb_reg(BVR,i) == (instruction_pointer & ~0x3)`，命中后把 `instruction_pointer` 存入 `counter->trigger` 并调 perf_bp_event→overflow handler（本模块自定义 handler），**只对默认 overflow handler 才 `step=1` 单步**。自定义 handler 返回后 ERET 回原 PC。
   - 场景 A（BVR 被恢复为旧地址 target_addr，而目标线程已停在返回点 LR 附近执行）：线程执行到 target_addr 时再次命中，handler 此时 `is_waiting_return` 分支或 skip 计数分支按逻辑处理——最坏多记/少记一次（错采一拍）。
   - 场景 B（BVR 被恢复为旧地址且线程不会再执行 target_addr）：槽武装但永不命中——静默丢监视，直至下一次 rearm_to（下一次完整调用时 :312 循环仍按 node->bp_addr 找槽——但注意 BVR 已被恢复成旧地址=orig_bp_addr，若 node->bp_addr 已被 rearm_to 写成 LR，则 :315 匹配失败 → `moved==0` → :329 打印 "no armed slot" → **节点 bp_addr 已更新但物理槽停在旧地址**）。
   - 场景 C（入口拍 rearm 到 LR 后立刻被上下文切换打断）：切换出时 `toggle_bp_registers` 清 bit0（bps_disabled），切回时恢复 bit0 并写 BVR=info->address=target_addr——线程回到 LR 后在 LR 处**不会**命中（BVR 已不是 LR），等到下次调用 target_addr 又命中一次——handler `is_waiting_return=1` 分支把这次入口当返回拍记 ret_x0。后果＝该次观察的 ret_x0 记到了**下一次**调用头上（错配一拍），且 rearm_to(orig_bp_addr) 把 BVR 改回 target_addr，状态机复位。**仍是错采，不是崩溃**。
2. **不会命中不存在的地址而异常递归**：BVR 恢复成的旧地址是当初 hook 注册时经 `sh_addr_is_valid` 校验的可执行用户地址（hwbp.c:569-577 校验 trampoline；hook 入口校验 target_addr，AUD-d-1），即使错采也是在合法代码地址上多触发一次 handler，handler 对任意 PC 的处理是幂等的状态机读写，无二次异常。
3. **重复命中循环**：由于命中匹配要求 PC==BVR，且 handler 处理后 ERET 回的 PC 是 handler 已处理过的位置（SKIP_ORIGIN 改 pc=lr、观察拍改写寄存器不改 pc、入口拍 rearm 走人），BVR 若恰好等于 ERET 目标 PC 会立即再命中一次并再次进入 handler——但 handler 每次进入都推进状态机（waiting_return 清位/rearm 换址/计数++），有限次内到达 `is_disabled` 或地址错开，**不存在不推进状态的无限循环**。真机 selftest hits=2、连续脚本无卡死佐证。

结论：该局限的实际后果域 = {多记/少记一次命中、ret_x0 错配一拍、监视暂时静默直至自愈}，均在「错采」范畴内，不产生内核崩溃/死循环。模块注释（:242-246）「错采一拍自愈」的表述**准确**，登记为残余风险可接受。触发条件（热插拔/休眠唤醒/断点线程跨 CPU 迁移且恰在窗口内）在手机使用场景为低频事件。

### 1e. disarm 路径完整性 —— **成立**

三条校验失败路径逐条核对（均先 disarm 再置位）：

| 路径 | 位置 | disarm | is_disabled |
| --- | --- | --- | --- |
| rearm_to 越界（`sh_user_addr_ok` 失败） | hwbp.c:360-366 | :363 `sh_hwbp_disarm_msr(matched→node)` | :364 |
| SKIP_ORIGIN LR 越界 | hwbp.c:416-420 | :417 | :418 |
| INLINE trampoline 越界 | hwbp.c:438-442 | :439 | :440 |

- disarm 的作用（:334-336 注释）：只置 is_disabled 不摘武装时，断点留在当前 PC，ERET 后立即重触发成调试异常死循环——R4g 把 disarm 放进所有失败路径，消除了这个隐藏死循环类。二进制验证 0x2824-0x2834（越界分支调用 disarm_msr 后 STR 0x44=is_disabled）与源码一致。
- **enable 命令重武装行为**（任务问）：`sh_hwbp_enable`（:643-669）只写 `is_disabled`（:657）并调 perf_event_enable/disable（:659-663），**不写 BVR**。disarm 后 BVR 仍指向断点最后所在地址（rearm_to 越界时=旧 target_addr 或最后一次 rearm 的地址）。因此：
  - 若失败发生在入口拍 rearm_to(lr) 之前（节点还在 target_addr），enable 后断点恢复到 target_addr——**语义正确**。
  - 若失败发生在 SKIP_ORIGIN LR 越界/观察拍 rearm 越界（此时 BVR 可能已在 LR 或已 disarm 于 target_addr），enable 后恢复到 BVR 当前值所指地址——可能是 lr（一个合法但非 target 的用户代码地址）或 target_addr。
  - 行为评估：enable 走的是**命令通道（进程上下文）**，前提是用户先收到失败通知（selftest/QUERY 的 is_disabled 标志，:657 写位可见）再 enable——属用户主动恢复，恢复到哪个地址取决于上次状态，**不产生内核风险**（地址必为之前 BVR 的合法用户值）。语义上"重新武装但地址可能偏移"与旧实现（perf enable 也会恢复 perf 记录地址，同样不保证是期望地址）**等价甚至更好**。可接受，建议在模块 README 残余风险里补一句「disarm 后 enable 恢复到 BVR 当前值，可能非 target_addr」。
- 唯一小瑕疵（不构成缺陷）：:417/:439 disarm 后无日志（rearm 路径越界也静默），运维排障时只能看到节点 is_disabled，看不到失败原因。列入 §6 建议。

### 1f. 隐藏 bug 检查 —— **带条件通过（两项遗留窗口，均非新增）**

1. **链表遍历 vs hook/unhook/retired 写**（异常上下文无锁）：
   - unhook（:618-641）置 `retired=1`/`is_disabled=1`/`bp_handle=0` 但**不摘链**——handler 遍历（:385-396）在无锁下读到的节点始终有效（cleanup 才 vfree，而 cleanup 在模块卸载进程上下文且已 unhook syscall 桥，见 §2）。ARM64 对齐的指针/布尔读写是原子的单写者场景，handler 读到半更新顺序最坏是：`retired=0,bp_handle=旧` → 走一次正常处理（事件多记一次）——**错采级，非崩溃**。
   - hook 尾插（:599-603）在命令通道（mutex 内，stealth_hook.c:261-269）；handler 并发遍历同样读到完整节点或看不到新节点——链表插入自身用 next/prev 双写，无 ABA。**窗口存在但后果限错采**。
   - cleanup（:820-838）摘链+put_task_struct+vfree 与并发 handler 的竞态：cleanup 只在 stealth_hook_exit（stealth_hook.c:462）执行，此前 `inline_unhook_syscalln`（:459）已把 syscall 桥卸掉，但**perf 断点仍在武装**——若目标线程恰在 cleanup 的 release→vfree 窗口命中断点，handler 引用已 vfree 节点 → **UAF**。这是遗留窗口（R4f 记录与此前审计均未单列），触发条件=模块卸载瞬间目标线程恰好执行断点地址且 release_kernel 尚未完成 UNINSTALL。`perf_event_release_kernel` 内部会先禁用事件再 UNINSTALL（BCR=0），窗口极窄但非零。**建议**（§6 新发现 NEW-g-1，low）：cleanup 先对每个节点 disarm_msr（异常上下文外调用安全）再 release。
2. **MSR 通道 vs perf API 通道互踩**：
   - 场景：异常上下文 rearm_msr 改 BVR 的同时，同 CPU 上进程上下文 enable/disable（perf_event_enable 走 IPI 或直接 hw_breakpoint_control）写同一槽 BCR。6.1 中 user hw_breakpoint 的 enable/disable 在事件所属 CPU 上下文执行（cpu=-1 绑定 task→当前 CPU），与断点命中本就互斥于同一 CPU 的异常粒度；跨 CPU 时 write_wb_reg 是本地寄存器写，不涉及目标 CPU 的 BVR/BCR（per-CPU 槽在**本** CPU 上）——**单 CPU 上 handler 与 sh_dispatch 不可能并发**（handler 是该 CPU 上的异常处理，sh_dispatch 是该 CPU 上的进程上下文，串行）；跨 CPU 时各自只碰本 CPU 槽，无交叉。**理论竞态面为零**，除 cleanup 场景（见 1）。
   - 唯一交叉点：`sh_hwbp_enable` 的 perf_event_enable 与异常上下文 rearm 的 BCR bit0 翻转都写同一槽 BCR。同 CPU 串行（见上），跨 CPU 不可能（事件绑定 task，enable 在 task 所在 CPU 执行）。**无缺陷**。
3. **单 CPU 上 handler 与 sh_dispatch 并发**：不可能（异常处理 vs 进程上下文在同一 CPU 天然串行）。sh_dispatch 持 mutex（stealth_hook.c:265-267）防的是**多核命令并发**，与 handler 无关。**成立**。

### 2a. cleanup 恢复位置 —— 正确

- `stealth_hook.c:452-466` `stealth_hook_exit()`：`inline_unhook_syscalln(...)`（:459）→ `sh_hwbp_cleanup()`（:462）→ `sh_ghost_cleanup()`（:463）。
- 位置语义：先卸 syscall 桥（此后新命令不可达）再清 hwbp 节点，最后清 ghost 映射。cleanup 放在 unhook 之后保证「卸载后活跃断点回调跳进已卸载模块」（AUD-e-4 原描述）的入口被关闭——**回调关闭先于释放**，顺序正确。
- ghost_cleanup 放最后合理：ghost 映射不依赖 hwbp 节点。

### 2b. 释放路径无 UAF/双释放 —— 成立（带一个理论窗口，见 §1f-1/NEW-g-1）

- `sh_hwbp_cleanup`（hwbp.c:810-840）：`bp_handle` 非零才 release（:824-830，release/unregister 二选一）→ 摘链（:831-832）→ `put_task_struct`（:833-835）→ `vfree`（:836）。
- **双释放**：unhook 路径 release 后置 `bp_handle=0`（:633），cleanup `if (node->bp_handle)` 判零跳过——unhook 过的节点不会二次 release ✓。cleanup 自身单遍历摘链（tmp 保存 next），链表节点释放后不再访问 ✓。
- **引用计数**：hook 成功路径 get_task_struct 一次（:564-567），cleanup put 一次（:833-835）；失败路径 put（:592-594）；unhook 不 put（节点未释放，task_ref 仍被 handler 可能引用）——**计数收支平衡** ✓。
- **released 计数**（:815、:837-839）：int 累加 + pr_info 一次，正确。
- 残余窗口：cleanup 与并发 handler 的 UAF（§1f-1），非 R4f 引入，单列 NEW-g-1。

### 2c. dump 兜底禁用 —— 正确

- `hwbp.c:488-497`：`!sh_copy_from_user_nofault` 时 static `dump_warned` 一次性 pr_warn + `break`（跳出寄存器循环，后续寄存器不再尝试）→ 本节点 dump 能力整体禁用，QUERY 的 mem_len 全 0 可观测。
- 消除了 R4b 遗留的「缺 nofault 符号回退 `__arch_copy_from_user`」——该回退在异常上下文可能睡眠（AUD-f-2 原判 medium）。现路径兜底为纯禁用，**异常上下文零睡眠点** ✓。
- `static int dump_warned` 无并发保护：异常上下文并发首次进入理论上可双打印一次——无副作用，接受。

## 3. AUD-c-5 复核 —— **误判应关**

**原单主张**（r1-c.md:109-117）：本地 `struct module`（battchg.h:142-149）name 偏移≈24，真实内核若开 `CONFIG_MODULE_UNLOAD` 等可能≈32，`memcmp(mod->name, MODULE_NAME, 20)` 永不匹配 → fallback 钩子静默失效。

**独立验证**（torvalds v6.1 `include/linux/module.h` 全文）：

1. `struct module` 开头三个成员顺序为：
   ```c
   enum module_state state;
   struct list_head list;
   char name[MODULE_NAME_LEN];   /* MODULE_NAME_LEN = 64 */
   ```
   **`name` 在任何 CONFIG_ 条件编译之前**，紧随 `list`。此后才是 `#ifdef CONFIG_STACKTRACE_BUILD_ID` 的 build_id、mkobj、`#ifdef CONFIG_MODULE_UNLOAD` 的 source_list/target_list/exit/refcnt 等——**全部在 name 之后**。
2. 因此原单「CONFIG_MODULE_UNLOAD 使 name 偏移从 24 变 32」的机制**不成立**：UNLOAD 成员根本不在 name 之前，不可能抬高其偏移。对 4.x/5.x/6.1 上游 `struct module`，name 偏移恒为 `sizeof(enum)+pad+sizeof(list_head)` = 4+4+16 = **24**（ARM64 上 enum=4B、list_head 8 对齐产生 4B pad；64 位平台一致）。
3. 本地结构 `char name[64 - sizeof(unsigned long)]`（=56）与上游 `char name[MODULE_NAME_LEN]`（=64）**尺寸不同**，但模块只用 `mod->name` 前缀做 memcmp 长度 20（"qti_battery_charger"+NUL，qti_battery_charger.c:73），读 20 字节远小于两种定义的最小值，越界面不存在（原单也已排除）。
4. 布局完整性的剩余变量：`CONFIG_GCC_PLUGIN_RANDSTRUCT`（`__randomize_layout` 标注）。该插件只随机化**含函数指针成员**的结构体，`struct module` 含 init/exit 函数指针可被随机化；但 Android GKI/Pixel 内核（包括目标 6.1.99-android14）不开 RANDSTRUCT（厂商内核用确定性布局，BTF/kallsyms 生态依赖稳定偏移）。此为环境性残余变量，非原单所指的 CONFIG_MODULE_UNLOAD 机制。
5. 功能侧旁证：该模块 fallback 只在 `battery_psy_get_prop` 直连符号失败时才依赖 do_init_module 钩子；do_init_module_after（qti_battery_charger.c:68-77）行为与偏移一致时的预期完全吻合。

**结论**：**误判，应关闭 AUD-c-5**（由发现方执行关闭，开发者反驳成立）。原单的"≈32"机制在上游源码中被直接证伪；name 偏移 24 是 `struct module` 从 4.x 到 6.1 的稳定标准布局。关闭时建议附注一条环境性残余：目标内核若启用 CONFIG_GCC_PLUGIN_RANDSTRUCT（Android 内核默认关）则 memcmp 失配——届时由动态推导覆盖，当前目标不受影响。
