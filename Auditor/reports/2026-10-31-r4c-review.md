## 2. 逐条复核

### 2.1 AUD-d-2：命令通道是否已完全不用关中断自旋锁；mutex 降级是否安全；与 syscall hook 上下文是否冲突 — **部分关闭**

**(a) 关中断自旋锁已完全移除 —— 已修。**
`stealth_hook.c:217-247`：`sh_spin_lock_fn/sh_spin_unlock_fn/sh_cmd_lock_area` 全部删除（对照 `git show 71d18c7` 的 −22 行），解析的是 `mutex_lock/mutex_unlock/__mutex_init`（:226-228）。全文件 `grep -n "spin\|irqsave" stealth_hook.c` 零命中。

**(b) mutex 与 syscall hook 上下文不冲突 —— 成立。**
唯一调用链是 `sh_syscall_before`（:263）→ `sh_dispatch`（:287）→ `sh_cmd_lock`（:253）。syscall hook 的 before 回调运行在被挂钩系统调用的**进程上下文**（非中断、非原子），`mutex_lock` 可睡眠是合法的；`sh_dispatch_body` 里的 `copy_from_user`/`vmalloc`/`vm_mmap`（`ghost_mem.c:121/128/185-208`、`hwbp.c:415`）不再违反原子约束。真机自检「scheduling while atomic 计数无新增」与此一致。

**(c) 无递归、无 early-return 漏 unlock —— 成立。**
`sh_dispatch`（:249-257）是 lock→body→unlock 的直线结构，`sh_dispatch_body` 的所有 `return` 都在锁的包裹之内，不存在中途 return 绕过 `sh_cmd_unlock` 的路径。递归检查：`sh_dispatch_body`（:140-212）只直呼 `sh_ghost_*`/`sh_hwbp_*`，这七个函数（`ghost_mem.c`、`hwbp.c` 全文）没有任何一处再进入 `sh_dispatch`/`sh_cmd_lock`，**无再入**，mutex 非递归不会自锁。

**(d) 但锁对象本身仍是裸字节 —— 残余（新开 AUD-e-1，§3.2）。**
`sh_cmd_mutex[8]`（:220，32 字节）不是 `struct mutex`。arm64 6.1 **非调试内核**的 `struct mutex`（owner 8 + wait_lock 4 + osq 4 + wait_list 16）恰好 ≈32 字节——零余量，`__mutex_init`（:233）不会越界；但在 `CONFIG_DEBUG_MUTEXES`/`CONFIG_LOCKDEP`/`CONFIG_DEBUG_SPINLOCK` 目标上 `struct mutex` 含 `dep_map`/magic 字段，**明显超过 32 字节**，`__mutex_init` 会写到数组后面的静态变量（`sh_cmd_mutex_ready`，:221 正好排在其后）。这正是上一轮对 `unsigned long[8]` 冒充 `spinlock_t` 的同一类批评，本轮只把对象换了个名字。目标 Pixel 6 生产内核大概率没开这些调试项，所以真机没炸——不能作为写法正确的证明（与 R4b 对自旋锁的论证同构）。

**(e) 懒初始化自身有竞态 —— 新开 AUD-e-2（§3.2）。**
`sh_cmd_lock`（:225-236）的 `if (!sh_cmd_mutex_ready) { …解析…init…ready=1 }` 没有任何同步。两条不同 CPU 上的首条命令可同时进入该分支：两次 `kallsyms_lookup_name` 无害，但两次 `__mutex_init(sh_cmd_mutex, …)` 并发会撕裂初始化（后到者可能在先到者已持锁时重置 `wait_lock`/`wait_list`）。窗口只在模块加载后的首两条命令，但这是修「串行化」的提交自带的串行化漏洞。

**(f) 缺符号降级仍是 fail-open —— 可接受但要记录。**
`sh_mutex_lock_fn` 置 0 后（:229-231）`pr_warn` 一次并全程不串行化：**互斥会静默消失，只剩一条日志**。任务书问「会不会静默失去串行化又没提示」——答案：不是完全静默（首条命令打一次 warn），但相比 KP 范式（`kp_spinlock.c` 降级后仍用 `local_irq_save + cmpxchg` 保证互斥）这里是「降级=失去保护」。`mutex_lock/mutex_unlock/__mutex_init` 三个符号在任何有 MMU 的 Linux 上都是 kallsyms 可查的常驻符号，缺任何一个的概率极低；判可接受，但按上一轮口径这仍是降级而非兜底，记录在案。

**判定：部分关闭。** 崩溃面（关中断下睡眠）确实消除，真机证据支持；但 (d)(e)(f) 三条残余都在同一函数 `sh_cmd_lock` 的 20 行里，修法都是几行的事，不建议带病进入 R5。

### 2.2 AUD-d-1：`sh_addr_is_valid` 能否挡住无效地址 panic；0x0000800000000000 是否正确；降级与绕过入口 — **部分关闭**

**(a) 校验本体 —— 已落地。**
`hwbp.c:91-121` 定义 `sh_addr_is_valid(task, addr)`；`sh_hwbp_hook` 在 `find_task_by_vpid` 之后、分配/注册之前调用（:410-413），失败 `return -22` 并 `pr_err`。注册前校验路径唯一且在其前无旁路：:392-409 的参数检查之后直接进入 :410，随后才 `vmalloc`/`perf_event_create_kernel_counter`（:415-437）。

**(b) 用户区间上限 0x0000800000000000 —— 正确（对目标）。**
arm64 `VA_BITS=48` 时 `PAGE_OFFSET = 0xffff800000000000 = -(1<<47)`，用户空间为 `[0, 2^47)`，即 `TASK_SIZE = 0x800000000000`；`SH_USER_ADDR_MAX = 0x0000800000000000`（:90）与半开区间 `addr >= SH_USER_ADDR_MAX → 拒绝`（:97）正好覆盖 `[0, 2^47)`，下界 `0x1000` 排除零页。**注意**：`CONFIG_ARM64_VA_BITS_52`（LVA）目标上合法用户地址可达 2^52，该上限会误拒高位地址——方向是 fail-closed（拒绝而非放行），可接受；本仓目标 6.1.99-android14（Pixel 6）为 48 位 VA，无影响。

**(c) 「能挡住无效地址导致的 panic」—— 部分成立。**
校验读一个完整指令字：同进程用 `copy_from_user_nofault`（:104，inatomic，不睡眠），跨进程用 `get_task_mm + access_remote_vm(mm, addr, &insn, 4, 0)`（:109-119），`mm==NULL`（内核线程）拒绝。未映射地址、内核地址、跨进程非法地址都会在注册前返回 `-22`，不再静默成功。但注意它只验证「可读」，不验证 VM_EXEC/可执行性——落在可读数据段的地址仍会注册成功（永不命中的假 hook）；这比「静默成功」好，但没有达到 R3 修法建议的「可执行 VMA」标准。真正的 panic 责任按 R4b 报告分析主要在 d-2/d-3 的睡眠与 perf 路径，本单的独立贡献是消除「把断点装到野地址」这一输入面。

**(d) 符号缺失降级 —— 有注释、fail-open，勉强可接受。**
同进程缺 `copy_from_user_nofault` → `return 1`（:101-103）；跨进程缺 `access_remote_vm` 或 `get_task_mm` → `return 1`（:106-108）。两处都有代码注释声明残余风险（:88-89 文件头 + :107 行注释），满足任务书「注明」的要求。但降级后校验只剩区间检查，无效地址重新静默通过——`copy_from_user_nofault` 在 5.10/6.1 均存在，`access_remote_vm/get_task_mm/mmput` 是内核非导出但 kallsyms 常驻符号，缺符号概率极低；判「可接受」。

**(e) 其它能绕过校验的入口 —— 有两处，未修。**
- `SH_HWBP_FLAG_INLINE`：`hwbp_handler` 直接 `regs->pc = matched->trampoline_addr`（:306），`trampoline_addr` 来自用户请求（:429），**从未经过任何校验**。攻击者（root）用合法 `target_addr` + 野 `trampoline_addr` 注册 INLINE hook，命中一拍后 PC 被送到任意值——与 R3 修法清单第 3 条（trampoline 校验）明确不符。
- `SH_HWBP_FLAG_SKIP_ORIGIN`：`hwbp_handler` 直接 `regs->pc = STRIP_PAC(regs->regs[30])`（:291），此处 LR 未校验（rearm 路径的校验在 :235，管的是断点重装，不管这条直接写 PC 的分支）。
- ENABLE（:494-520）/OVERRIDE（:590-625）/SET_SKIP（:627-646）不修改任何断点地址，只改 `is_disabled`/参数/计数，**不构成地址旁路**。

**判定：部分关闭。** HOOK 主入口已封；INLINE trampoline 与 SKIP_ORIGIN 的 pc 写入是同级别的「未校验地址进 PC」，应随 medium/low 批量一并收口（各加一次 `sh_addr_is_valid` + 不合格置 `is_disabled` 即可）。

### 2.3 AUD-d-3：rearm 校验失败置 is_disabled 是否足够；LR 指向内核/伪造值；异常上下文还有没有 perf API — **部分关闭（残余 high）**

**(a) rearm 目标校验 —— 已落地。**
`rearm_to`（:228-249）在改 `bp_addr` 之前调 `sh_addr_is_valid(node->task_ref, addr)`（:235），失败置 `node->is_disabled = 1` 并返回（:237-238）。`node->task_ref` 是 hook 目标线程（带自持引用，:424-427），跨进程场景下在目标 mm 里验 LR 可读性，方向正确。两个调用点（返回拍 :314、入口转 LR 拍 :324/:374）都经过它。

**(b) LR 来自 regs[30] 指向内核/伪造值 —— 已挡。**
内核地址被区间检查拒绝（:97，`0xffff…` > `SH_USER_ADDR_MAX`）；`STRIP_PAC`（:41）把带 PAC 的 LR 变成低 48 位后仍在区间检查覆盖之内。用户伪造 LR 到不可读地址也会被可读性检查拒绝。

**(c) 但 perf API 仍在异常上下文 —— 上一轮的核心指控未修，仍开。**
`rearm_to` 体内仍是 `sh_perf_event_disable` → `sh_modify_user_hw_breakpoint` → `sh_perf_event_enable`（:242-248），其中 `modify_user_hw_breakpoint` 内部走 `perf_event_ctx_lock()` → `mutex_lock(&ctx->mutex)`（可睡眠），`perf_event_disable/enable` 对运行在其它 CPU 的事件走 `task_function_call` 自投 IPI。`rearm_to` 的调用者 `hwbp_handler`（:252 自注「运行在调试异常上下文（原子、不可睡眠）」）。R4c 只在 perf 调用**之前**加了校验，**没有把 perf 调用挪出异常上下文**——R4b 报告 §3.3 的最小修法（irq_work/task_work 延后，或双固定断点免 modify）完全未实施。真机 selftest 通过只能说明当次 mutex 无争用（「碰巧没炸」）。
**(d) 三个 perf 返回值依旧未检查**（:242-248），rearm 失败后节点不自知，`is_waiting_return` 已置 1（:373），事件若 disable 后 modify 失败，断点永久哑掉且 query 显示正常——语义缺口未变。

**判定：部分关闭，残余维持 high。** (a)(b) 是新增的防护（值得肯定，它确实堵住了「LR 装到野地址」这一子面），但本单的定义性危害——「调试异常上下文里调可睡眠 perf API」——原样保留。

### 2.4 AUD-d-4：GHOST_LIST 只给 root 是否等价解决 — **已关闭**

`stealth_hook.c:148-152`：

```c
/* ghost 建的是可写/可执行 VMA，LIST 也会泄露别人的映射，整组只给 root
 * （AUD-b-1 / AUD-d-4 复核意见） */
if (cmd >= SH_CMD_GHOST_ALLOC && cmd <= SH_CMD_GHOST_LIST) {
    return -1;
}
```

`stealth_hook.h:69-72` 定义 `GHOST_ALLOC=0x3001 / FREE=0x3002 / WRITE=0x3003 / LIST=0x3004`，连续无洞，区间覆盖到 LIST；门在唯一分发点 `sh_dispatch_body` 顶部（:144），非 root 的 `GHOST_LIST` 在到达 `sh_ghost_list`（`ghost_mem.c:215-242`，该函数本身未按 pid 过滤、仍遍历全局链表）之前就被拒。真机自检 `shell ghost list → EPERM` 与代码一致。采用「整体关门」而非「按 pid 过滤」，对本单目标（任意 uid 列举别人的 ghost 段）等价且更简单。**判定：已关闭。**

### 2.5 AUD-b-3：retired 语义是否还有双重 release 或对已释放对象的访问 — **部分关闭**

**(a) 双重 release —— 已关闭**（R4b 已修，本轮重验仍在场）：
- `sh_hwbp_unhook`：`retired` 检查在 release 之前（`hwbp.c:474-476` return -2），`bp_handle` 在 release 后立即置零（:477-484）；
- `sh_hwbp_cleanup`：只在 `node->bp_handle` 非零时释放（:666-672）；
- `rearm_to`：`!node->bp_handle` 早退（:232）。
正常（无并发）路径上无双重 release、无对已释放句柄的调用。真机「hook/unhook 后 unload rc=0、管理器存活」在 R4b 已是该子项的现场证据。

**(b) enable/query 跳 retired —— 仍在场**（:504-506、:543-545）。

**(c) 残留 1：`set_override`（:605-624）与 `set_skip`（:635-644）仍不跳 retired**——对已退役节点继续写 `override_mask/override_args/ret_value/flags/skip_count`。只写字段不碰 `bp_handle`，无 UAF、无二次释放，属语义混乱（R4b 报告 §2.4(b) 已点名，本轮 commit message 自认「沿用 R4b 的 retired 语义，仅把串行化实现换成 mutex」，即有意未修）。维持 low 残留。

**(d) 残留 2：handler 与命令通道的竞态依旧零同步。** `hwbp.c` 全文件 `grep -n "mutex\|spin\|WRITE_ONCE\|smp_\|barrier"` 零命中（仅误中 `clockid`）。`rearm_to` 读 `node->bp_handle`（:232）与 `sh_hwbp_unhook` 的 release+置零（:477-484）之间窗口未收窄（`is_disabled=1` 在 release 之**后**才写，:487——handler 若已在 :232 读到非零句柄，仍可能对已 release 的 event 调 :242-248 三个 perf API）。这是 R4b §2.4(c) 第 4 点的原文，本轮未处理。窗口窄（需 unhook 与断点命中同拍），单独不足以维持 high，但与 (c) 一起说明本单只剩「形式上的 retired」，缺的正是真同步。

**判定：部分关闭。** (a)(b) 子项稳定关闭且有真机证据；(c)(d) 为已知残留，实现方本轮明确未碰。

## 3. 新发现问题

### 3.1 AUD-e-3：`sh_addr_is_valid` 的跨进程路径把可睡眠的 `access_remote_vm` 引进了调试异常上下文 —— **high（R4c 新引入）**

- 位置：`hwbp.c:114`（`sh_access_remote_vm(mm, addr, &insn, 4, 0)`）被 `rearm_to`（:235）在 `hwbp_handler`（调试异常上下文，原子）里调用。
- 机制：`access_remote_vm` → `get_user_pages_remote` → `mmap_read_lock(mm)`（读写信号量，**可睡眠**）+ 可能的 GUP 页表遍历/缺页处理。同进程分支（`copy_from_user_nofault`，:104）是 inatomic 的、安全；跨进程分支不是。目标线程 ≠ `current` 时（跨进程 hook，本模块明确支持的用法：AUD-b-1 注释「跨进程 hook 必须 root」），第一次断点命中转 LR 的 `rearm_to`（:374）就会在异常上下文里走这条睡眠路径——`CONFIG_DEBUG_ATOMIC_SLEEP` 内核直接报 `BUG: sleeping function called from invalid context`，`panic_on_warn=1` 即 panic。
- 定级 **high**：`frequency: 中`（仅跨进程 hook 且断点命中时触发；自测全程是自进程 hook 所以没炸）；`confidence: 高`（调用链确定，`access_remote_vm` 的睡眠语义确定）。这正是 AUD-d-3 的未修残留在新代码上的具象化：**修 d-1 的函数被搬进了 d-3 的原子上下文，而它自己就是可睡眠的**。
- 最小修法（交回 Developer）：rearm 的跨进程校验不能直接调 `access_remote_vm`——把校验/重装挪到 `irq_work`/workqueue；或 rearm 路径退化为「仅区间检查 + 白名单（`orig_bp_addr` 或已验过的 LR 集合）」；或干脆双固定断点免 modify。三者任选其一都必须同时解决 §2.3(c) 的 perf-in-atomic，因为它们在同一个函数里。

### 3.2 AUD-e-1 / AUD-e-2：`sh_cmd_lock` 的锁对象与初始化 —— **low / low**

- **AUD-e-1**（low→视目标内核配置可到 medium）：`sh_cmd_mutex[8]`（`stealth_hook.c:220`）是 32 字节裸数组。非调试 arm64 6.1 内核 `struct mutex` 恰约 32 字节（零余量）；`CONFIG_DEBUG_MUTEXES`/`CONFIG_LOCKDEP`/`CONFIG_DEBUG_SPINLOCK` 目标上超界，`__mutex_init`（:233）会踩到紧随其后的 `sh_cmd_mutex_ready`（:221）。修法：改为按 KP 头文件里真实 `spinlock_t`/`mutex` 类型声明（KP 已提供类型与 `spin_lock_init`），或至少把数组放大到 128 字节并 memset 后 init，同时在注释里写死「假定尺寸」的验证方式。
- **AUD-e-2**（low）：`sh_cmd_lock` 的懒初始化（:225-236）无同步，两条 CPU 上的首条命令可并发进入，`__mutex_init` 并发两次撕裂锁。修法：模块 `init`（:294-316，单线程上下文）里一次性 `sh_cmd_lock` 初始化，运行期只走锁路径；或用静态初始化范式。
