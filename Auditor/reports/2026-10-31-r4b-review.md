## 2. 逐条复核

### 2.1 AUD-a-6（info）`mod_control0` 截断后不补 NUL — **已关闭**

**判定：已关闭。**

依据 `modules/KPM/memcrc/mod_main.c:94-113`：

```c
if (out_msg && outlen > 0) {
    int len;
    if (buf[0]) { snprintf(buf + strlen(buf), sizeof(buf) - strlen(buf), " rc=%d", rc); }
    else       { snprintf(buf, sizeof(buf), "rc=%d", rc); }

    len = (int)strlen(buf);
    if (len >= outlen) {
        len = outlen - 1;   /* 留 1 字节给 NUL（AUD-a-6） */
    }
    buf[len] = '\0';        /* 先在内核侧补 NUL，再连 NUL 一起拷（AUD-a-6 复核意见） */
    if (len > 0) {
        if (!compat_copy_to_user(out_msg, buf, len + 1)) {
            return -EFAULT; /* KP 语义：返回 0 表示拷贝失败 */
        }
    }
}
```

- ① 外层 `out_msg && outlen > 0`（:94）保证 `len = outlen-1 ≥ 0`，不存在负下标写 `buf[-1]`；② `len+1 ≤ outlen` 且 `len ≤ strlen(buf)`，`buf[len]` 必在数组内；③ 顺序正确：先在内核侧写 NUL，再 `copy_to_user(..., len+1)`。三项要求全部满足。
- 交叉核对调用方：KP `KernelPatch/kernel/patch/common/supercmd.c:423` 是 `char buffer[4096]`、`:424` 先 `buffer[0]='\0'`，`:488` 以 `sizeof(buffer)`（4096）作 `buflen` 传进 `handle_cmd_key_auth`，再到 `:297-299` `module_control0(name, mod_args, buffer, buflen)`、`cmd_res->msg = buffer`（按 C 串读）。因此「带 NUL 拷」是本路径的**功能必需**，不是洁癖；`buflen=4096` 时模块消息（<256B）永不截断，本单实害为 0（info 定级正确）。另一路径 `KernelPatch/kernel/patch/common/supercall.c:87-93` 把用户传入的 `outlen` 直接透传，`outlen ≤ 0` 被 :94 守卫挡掉，也不会出负下标。
- 残留（info，不阻塞）：`outlen == 1` 时 `len == 0`，`if (len > 0)` 使整段不拷，用户缓冲连终止 NUL 都不写。若调用方未预置 `'\0'` 会读到脏串；KP 路径 `buffer[0]='\0'` 已挡住。建议（可选）：把 `if (len > 0)` 改为无条件 `copy_to_user(out_msg, buf, len + 1)`，`len==0` 时正好只写一个 NUL。

### 2.2 AUD-b-1（high）命令门是否覆盖 ghost 建映射/写内存，shell 是否已无法建可写/可执行 VMA — **已关闭**

**判定：已关闭。**

依据 `modules/KPM/stealth_hook/stealth_hook.c:140-152`：

```c
if (sh_current_uid() != 0) {
    if (cmd >= SH_CMD_HWBP_HOOK && cmd <= SH_CMD_HWBP_SET_SKIP) {
        return -1;
    }
    /* ghost 建的是可写/可执行 VMA，同样只给 root（AUD-b-1 复核意见） */
    if (cmd >= SH_CMD_GHOST_ALLOC && cmd <= SH_CMD_GHOST_WRITE) {
        return -1;
    }
}
```

- 命令号区间：`stealth_hook.h:69-72` 定义 `GHOST_ALLOC=0x3001 / FREE=0x3002 / WRITE=0x3003 / LIST=0x3004`，`0x3001-0x3003` 连续命中，**建映射（alloc）、写内存（write）、释放（free）三个原语对非 root 全部关闭**；`0x1001-0x1007`（HWBP 全系，含 set_override/set_skip）同样关闭。
- 门的位置在**唯一分发点**：`sh_dispatch_body` 由 `sh_dispatch`（:238-247）调用，`sh_dispatch` 只被 `sh_syscall_before`（:253-278）在 :277 调用；ctl0 通道（:308-360）只处理 allow/deny/allowlist/status，不触达 ghost/hwbp。故不存在绕过门的分发路径。
- 身份判定可信：`sh_current_uid()`（:42-46）直接读 `current->cred->uid`（经 `task_struct_offset.cred_offset` / `cred_offset.uid_offset`），在 syscall hook 上下文里 `current` 即调用者；`sh_is_privileged`（:48-63）只把 uid 2000 放进「可进命令通道」，真正的 ghost/HWBP 门仍要求 `uid == 0`。即：**shell(2000) 连 `ghost alloc` 都到不了 `sh_ghost_alloc`**，与真机 `errno=1`（EPERM）一致。
- 「shell 无法建可写/可执行 VMA」成立：`ghost_mem.c:95-145` 的 `sh_ghost_alloc` 用 `vm_mmap(..., 0x22|MAP_FIXED, ...)`（:121）建匿名 RWX VMA，是模块内唯一建可执行映射的入口；PTE 三命令（`0x2001-0x2004`）对 shell 开放但 `stealth_hook.c:166-173` 一律返回 `-95`（`-EOPNOTSUPP`），不产生映射。
- 残留（低，另开 AUD-d-4）：`GHOST_LIST=0x3004` 仍在门外，`ghost_mem.c:215-242` 遍历**全局** `ghost_list` 且不按 mm/pid 过滤，uid 2000 可枚举 root 创建的 ghost 区域（va/size/pid/prot）。只读、无写原语，定 low。
- 最小修法（如要收口残留）：在 `sh_dispatch_body` 里把 `cmd == SH_CMD_GHOST_LIST` 也纳入 `uid != 0 → return -1`，或在 `sh_ghost_list` 内按 `node->pid == current->pid` 过滤。

### 2.3 AUD-b-2（high）调试异常上下文的用户读取 — **已关闭**

**判定：已关闭。**

依据 `modules/KPM/stealth_hook/hwbp.c:289-317`（`hwbp_handler` 内，该函数 :205 自注「运行在调试异常上下文（原子、不可睡眠）」）：

```c
if (matched->dump_size && sh_copy_from_user) {
    ...
    for (i = 0; i < 8; i++) {
        uint64_t ptr = regs->regs[i];
        ...
        if (ptr < 0x100000ULL || ptr > 0x7FFFFFFFFFFFULL) { continue; }
        if (sh_copy_from_user_nofault) {
            left = sh_copy_from_user_nofault(matched->mem_dump[i], (const void *)(uintptr_t)ptr, dn);
        } else {
            /* 兜底：__arch_copy_from_user 也有异常表，坏指针只少拷；
             * 但缺页可能触发 "sleeping function called from invalid context" 告警。 */
            left = sh_copy_from_user(matched->mem_dump[i], (const void *)(uintptr_t)ptr, dn);
        }
        if (left <= dn) { matched->mem_len[i] = (uint16_t)(dn - (uint32_t)left); }
    }
}
```

- 符号解析：`hwbp.c:148-149` 用 `kallsyms_lookup_name("copy_from_user_nofault")`；`:76-79` 的声明与 `:77-78` 注释说明「KP 未转发，仍走 kallsyms」。符号存在时**不再走可缺页路径**：该函数内部走 `__copy_from_user_inatomic()`（关缺页、不做 fault-in），坏指针只返回 `-EFAULT`，不睡眠、不触发 `do_page_fault`。上一轮「页存在但需 fault-in 会睡」的崩溃面在该分支上消除。
- 兜底注释明确：:308-312 既有功能兜底（异常表保证坏指针不崩），也有**文字注释**声明残留风险（缺符号时仍可能报 `sleeping function called from invalid context`），满足任务书「缺符号时的兜底是否被明确注释」。
- 语义核对：真实原型 `long copy_from_user_nofault(void *dst, const void __user *src, size_t size)` 返回 `0 / -EFAULT`，模块按 `unsigned long (*)(void*, const void __user*, unsigned long)` 调用，arm64 ABI 上一致；`left <= dn` 判定（失败时 `left = (unsigned long)-EFAULT` 极大，条件不成立，`mem_len` 保持 0）语义正确，不会出现「失败却记成正长度」。
- 残留（低，不阻塞，建议顺手改）：:291 的开关键仍是 `sh_copy_from_user`（即 `__arch_copy_from_user`）。若某目标只有 `copy_from_user_nofault` 而没有 `__arch_copy_from_user`，dump 会被静默关掉；反之若两者都缺，`sh_hwbp_resolve()`（:142-185）不把二者纳入必需集，dump 静默失效而 hook 仍返回成功。最小改法：`if (matched->dump_size && (sh_copy_from_user_nofault || sh_copy_from_user))`，并在 resolve 时对「两者皆缺」打一次 `pr_warn`。

### 2.4 AUD-b-3（high）命令通道串行化 / 重复 unhook / retired 跳过 — **部分关闭**

**判定：部分关闭。** 三个子项中两个落地且正确，第三个「串行化」形式上落地但实现不可接受，并引入新缺陷（AUD-d-2）。

**(a) 重复 unhook 返回 -2 且不再二次 release —— 已修，正确。**
`hwbp.c:423-438`：

```c
if (node->target_addr == target_addr && (tid == 0 || node->tid == tid)) {
    if (node->retired) {
        return -2;   /* 已退役：不重复 release（NEW-b-3a） */
    }
    if (node->bp_handle) {
        if (sh_perf_event_release_kernel) { sh_perf_event_release_kernel(node->bp_handle); }
        else if (sh_unregister_hw_breakpoint) { sh_unregister_hw_breakpoint(node->bp_handle); }
    }
    node->bp_handle = 0;   /* 已 release，置零避免 cleanup 二次 release（NEW-b-3a） */
    node->retired = 1;
    node->is_disabled = 1;
    return 0;
}
```

`retired` 检查在 release **之前**，`bp_handle` 在 release **之后立刻置零**；`sh_hwbp_cleanup`（:604-630）只在 `node->bp_handle` 非零时释放，两处合起来消除双重 release。与真机「先 hook/unhook 再 unload → rc=0、管理器进程不再僵尸」吻合。

**(b) enable / query 跳过 retired —— 已修，正确。**
`hwbp.c:454-456`（enable）与 `:493-495`（query）各有一句 `if (node->retired) { continue; }`，位于匹配判断之前，故不会再对已释放句柄调 `perf_event_enable/disable`（:459-465）。
残留（低）：`sh_hwbp_set_override`（:555-573）与 `sh_hwbp_set_skip`（:585-594）**仍不跳过 retired 节点**，会对退役节点继续写 `override_mask/override_args/ret_value/flags/skip_count`。两者只写字段、不读 `bp_handle`、不释放内存 → 无 UAF、无二次释放，属语义混乱（对已退役节点改参数不生效）。最小改法：两个循环里各补一句 `if (node->retired) continue;`。

**(c) 命令通道串行化 —— 形式落地，实现不可接受（判「部分关闭」的理由）。**
`stealth_hook.c:213-247`：

```c
static unsigned long (*sh_spin_lock_fn)(void *lock);
static void (*sh_spin_unlock_fn)(void *lock, unsigned long flags);
static unsigned long sh_cmd_lock_area[8];

static unsigned long sh_cmd_lock(void)
{
    if (!sh_spin_lock_fn) {
        sh_spin_lock_fn = (typeof(sh_spin_lock_fn))kallsyms_lookup_name("_raw_spin_lock_irqsave");
        sh_spin_unlock_fn = (typeof(sh_spin_unlock_fn))kallsyms_lookup_name("_raw_spin_unlock_irqrestore");
        if (!sh_spin_lock_fn || !sh_spin_unlock_fn) {
            pr_warn("[stealth_hook] no spinlock symbols, command path unserialized\n");
        }
    }
    return sh_spin_lock_fn ? sh_spin_lock_fn(sh_cmd_lock_area) : 0;
}

static long sh_dispatch(long cmd, long arg1, long arg2, long arg3, long arg4)
{
    unsigned long flags = sh_cmd_lock();
    long ret = sh_dispatch_body(cmd, arg1, arg2, arg3, arg4);
    sh_cmd_unlock(flags);
    return ret;
}
```

1. 「经 kallsyms 解析 + 无符号降级并告警」两个要求**字面满足**：`:222-223` 解析，`:224-226` 打 `pr_warn` 后降级为不加锁，`:228` 返回 0。作为「两路命令互斥」在符号存在时确实能串起来。
2. 但 `unsigned long sh_cmd_lock_area[8]` 是**裸字节冒充 `spinlock_t`**。本仓库既有范式是 `KernelPatch/kernel/patch/common/kp_spinlock.c`：同样走 `kfunc(_raw_spin_lock_irqsave)`，但对象是真正的 `spinlock_t`，且**降级路径仍然互斥**（`kp_local_irq_save` + `cmpxchg` 自旋）。本模块的降级是「完全不互斥」，与 KP 范式不同。更关键的是 `KernelPatch/kernel/linux/include/linux/spinlock.h:21-27` 的 `spinlock_t` 只有 4 字节（`:33` `DEFINE_SPINLOCK`、`:35` `spin_lock_init`）；本模块传 32 字节虽然不会越界，但在 `CONFIG_DEBUG_SPINLOCK` 目标上 `_raw_spin_lock_irqsave` 会走 `debug_spin_lock_before()` 的 magic 校验并 `SPIN_BUG_ON`（直接 `BUG()`），在 `CONFIG_LOCKDEP` 目标上会碰未初始化的 `dep_map`。真机上 `status/echo/hook/ghost` 全部返回正常，只能说明该目标没有开这两个调试项，不能作为「写法正确」的证明。
3. **真正的问题在临界区内容**：`sh_dispatch` 把**整段** `sh_dispatch_body` 包进 `preempt_disable + IRQ off` 的裸锁，而这条路径上的业务函数会睡眠：
   - `sh_ghost_alloc` → `ghost_mem.c:121` `sh_vm_mmap(...)`（取 `mmap_lock`，`vm_mmap` 可睡眠）/ `:128` `sh_vmalloc`（`GFP_KERNEL`，可睡眠）；
   - `sh_ghost_write` → `ghost_mem.c:185-208` 分块 `copy_from_user`（可缺页睡眠）；
   - `sh_ghost_free` → `ghost_mem.c:160` `sh_vm_munmap`；
   - `sh_hwbp_hook` → `hwbp.c:346` `copy_from_user`、`:365` `vmalloc`、`:383-387` `perf_event_create_kernel_counter`（内部 `perf_event_ctx_lock` → `mutex_lock(&ctx->mutex)`）；
   - `sh_hwbp_unhook` → `:427-433` `perf_event_release_kernel`（`mutex_lock(&ctx->mutex)`，且可能 `synchronize_rcu`）。
   在 `preempt_count > 0` 且本地中断关闭的状态下取 `mutex`，最低代价是 `might_sleep()` 报 `BUG: sleeping function called from invalid context`（`panic_on_warn=1` 的机器直接 panic）；一旦真的争用而 `schedule()`，就是 `BUG: scheduling while atomic`——锁仍被持有、中断仍关闭，其它 CPU 会在这把锁上自旋到看门狗（`watchdog_thresh` 默认 10s → soft lockup 约 20s、hard lockup 约 10s）报 lockup 并 panic。**这与 AUD-d-1 现场「adb 消失约 25 秒后回来」的形态吻合**（见 §3.1）。
   反证也成立：R4b 真机 selftest 里 `hook/hit/改参/跳过原函数/unhook` 全过，说明那次执行中 mutex 都没争用、`might_sleep()` 也没报，属于「碰巧没炸」，不是「写得对」。
4. handler 与 unhook 的句柄竞态**未处理**：`rearm_to`（`hwbp.c:187-203`）先读 `node->bp_handle`，再三次使用它；中间的 `unhook`（`hwbp.c:427-434`）可以 `perf_event_release_kernel(bp_handle)` 并置零。handler 读到非零值后继续用，就是对**已释放 perf_event** 调 `perf_event_disable/modify/enable`。窗口窄但真实，且 `hwbp.c` 全文件零锁、零屏障（`grep -n "spin\|mutex\|rcu_\|WRITE_ONCE\|smp_mb\|barrier" modules/KPM/stealth_hook/hwbp.c` 无命中），`retired` 也是普通写。

**最小修法（按性价比排序）：**
1. 临界区只留链表/状态迁移：`hook` 走「锁外建节点+注册 perf → 锁内发布到链表」，`unhook` 走「锁内摘链+置 retired → 锁外 release perf」；`ghost_alloc/write/free` 的 `vm_mmap/copy_from_user/vmalloc` 全部移到锁外（它们本就只在当前 mm 上操作，互斥需求来自链表，不是这些调用）。
2. 锁对象换成真 `spinlock_t`（`DEFINE_SPINLOCK` / `spin_lock_init`），沿用 `kp_spinlock.c` 的降级范式（符号缺失时仍用 `local_irq_save + cmpxchg` 保证互斥），不要用 `unsigned long[8]`。
3. `rearm_to` 的 perf 调用不要在异常上下文做（见 AUD-d-3）；若暂时保留，至少对 `bp_handle` 做 `READ_ONCE` 快照 + `retired` 双检，并把 `unhook` 的 release 延后到 `irq_work`/workqueue。
4. `set_override` / `set_skip` 补 retired 跳过（见 (b) 残留）。

### 2.5 AUD-b-5 / NEW-b-5a（low）perf 注册失败路径 — **已关闭**

**判定：已关闭**（限定于本单要求的失败路径；另有低残留）。

依据 `hwbp.c:374-398`：

```c
if (sh_get_task_struct) {
    sh_get_task_struct(task);   /* 之后线程退出也不会把 task_struct 释放掉（AUD-b-5） */
    node->task_ref = task;
}
...
if (!node->bp_handle || (uint64_t)node->bp_handle >= (uint64_t)-SH_MAX_ERRNO) {
    long err = node->bp_handle ? (long)(uintptr_t)node->bp_handle : -5;
    pr_err("[hwbp] register failed: ...");
    if (node->task_ref && sh_put_task_struct) {
        sh_put_task_struct(task);   /* NEW-b-5a：失败路径不漏 task 引用 */
    }
    sh_vfree(node);
    return err;
}
```

- 顺序正确：先 `put_task_struct` 再 `vfree(node)`，不存在「先释放节点再解引用 `node->task_ref`」的窗口（守卫读 `node->task_ref` 发生在 `vfree` 之前）。
- 失败路径穷举：`get_task_struct` 之前的所有早退（`-14` 拷贝失败、`-22` 参数、`-95` 符号、`-3` 找不到 task、`-12` vmalloc 失败）都没有持有引用；`get` 之后只有 perf 注册失败这一条出口，已补 put。**本单所指的引用泄漏已消除**（上一轮描述是「每次 hook 失败泄一个引用」）。
- 残留（low，不阻塞，建议随 medium/low 清理）：`sh_hwbp_resolve()`（`hwbp.c:179-183`）的必需集只要求「register 或 counter 之一」+「unregister 或 release 之一」，`get_task_struct`/`put_task_struct` 缺失时只是**静默**跳过保护（`if (sh_get_task_struct)`），AUD-b-5 的 UAF 防护会无声失效。最小改法：把 get/put 纳入必需集（缺则 `return 0` → hook 返回 `-95`），或在缺失时 `pr_warn` 一次。

## 3. 新发现问题

### 3.1 AUD-d-1（新）：`sh_hwbp_hook` 不校验 `target_addr` 可执行性 —— **high**

**现象**：真机对无效地址下 exec 硬件断点（`stealth_cli hook 0x2247d0`）后设备重启，adb 断开约 25 秒后恢复（`docs/records/2026-10-31-final-scope-and-delivery-plan.md:188-190`）。

**代码事实（无校验）**：`hwbp.c:346-354` 的全部入参校验只有三条：

```c
if (!sh_copy_from_user || sh_copy_from_user(&req, ureq, sizeof(req))) { return -14; }
if (!req.target_addr || !req.target_pid) { return -22; }
if (!(req.flags & SH_HWBP_FLAG_EXECUTE)) { return -22; }
```

之后直接 `find_task_by_vpid` → `vmalloc` → `fill_execute_attr(&attr, req.target_addr, ...)` → `perf_event_create_kernel_counter`（:359-387）。整个模块对 `find_vma|VM_EXEC|vm_flags|get_task_mm|mmput` **零命中**，即：不查 `target_addr` 是否落在目标进程的可执行映射内，也不查 `trampoline_addr`（:379）与后续 rearm 目标 `STRIP_PAC(regs[30])`（:322-328）是否可执行。

**「perf 断点打在非法地址上是否会触发不可恢复异常」——不会（这一点必须说清，否则会误修）：**
- arm64 的 `arch_build_bp_info()` 对用户态地址只校验「4 字节对齐 + `bp_len == HW_BREAKPOINT_LEN_4`」（对齐不满足才 `-EINVAL`）；只有 `is_kernel_addr(addr)` 的 X 断点才会用 `kallsyms_lookup_size_offset()` 验证是不是真实指令地址。**用户地址不做 VMA/页表检查**，所以 `0x2247d0` 这种 4 对齐的野地址会**注册成功**，`sh_hwbp_hook` 返回 0。
- 硬件断点是「取指地址比较」，目标地址没有指令被执行就永远不会命中。因此**仅仅把一个非法地址装上断点，不会产生任何异常**，更不会 panic；它的直接后果是「静默成功、永远不命中、使用者误以为已挂上」。
- 所以现场重启的崩溃点另有其处，最可能是本轮新开的两条：**AUD-d-2**（hook/unhook 全程在关中断自旋锁内取 mutex/vmalloc/mmap_lock，争用即 `scheduling while atomic` + 锁被永久持有 → 看门狗约 20s 后报 lockup 并 panic，与「25 秒后回来」的形态吻合）与 **AUD-d-3**（`rearm_to` 在调试异常上下文取 `ctx->mutex`）。**注意：如果只按计划文档加「可执行映射校验」，这次重启大概率仍会复现**——因为非法地址根本不会命中，崩溃发生在注册/释放路径上。

**定级：high**（`frequency: 高`——任意一条 `hook` 命令都会走这条无校验路径；`confidence: 中`——重启的**入口**是这条路径，但内核侧的确切崩溃点未取证，归因待 pstore/dmesg）。
理由：①现场已复现「设备重启」这一最高影响（设备不可用、需重启，可能丢数据），按 AGENTS「确认可致崩溃的问题不许因为不知道频率而降级」，不能定 medium/low；②不定 critical：模块命令通道已限 uid 0（AUD-b-1），无提权、无跨权限边界，且需显式命令触发；③它也承担「校验缺失导致误用」的独立责任：`0x2247d0` 这类硬编码地址在 ASLR/PIE 下极易落到**别的可执行映射**上，一旦命中，handler 会把 `pc` 改成 `STRIP_PAC(LR)` 并 `rearm_to` 到该 LR（同样未校验），或按 `INLINE` 标志改成用户给的 `trampoline_addr`——这三处都是「未校验地址直接进 PC」。

**最小修法（不要自己改，交给 Developer）：**
1. 注册前校验（fail-closed）：`mm = sh_get_task_mm(task)`（内核线程 `mm == NULL` → `-EINVAL`）→ `mmap_read_lock(mm)` → `vma = sh_find_vma(mm, req.target_addr)`，要求 `vma && (vma->vm_flags & VM_EXEC) && req.target_addr + 4 <= vma->vm_end`；不满足返回 `-EINVAL` 并 `pr_err` 打印实际 `vma` 信息。`get_task_mm`/`mmput`/`find_vma` 都是可 kallsyms 解析的符号；**任一符号缺失时拒绝注册**，不要沿用现在这种「缺符号就跳过校验」的 fail-open。
2. 同一校验复用到 rearm 目标：`hwbp.c:322-328` 在 `rearm_to(matched, lr)` 之前校验 `lr` 是否落在同一 mm 的可执行 VMA 内，不合格就**不 rearm** 并置 `is_disabled = 1`（宁可断点失效，也不要把 pc 送进野地址）。
3. `trampoline_addr`（`SH_HWBP_FLAG_INLINE`）同样校验；`dump_size` 已有 `SH_DUMP_MAX` 钳制，可不动。
4. 与 AUD-d-2/d-3 一起修，否则「加了校验」只会把重启变成偶发。
5. 取证前置：本轮未见该次重启的 pstore/dmesg 摘要（计划文档只写「怀疑内核 panic」）。按 `docs/process/07-escalation-device.md` 与 `Tester/README.md:29-30`，应先补采 `pstore`/`last_kmsg`（含 `boot_id`、`uptime`、是否有新增转储）再定因；**在定因前不要在真机上重复下无效地址断点**（AGENTS：死机不自救，禁止反复重试）。

### 3.2 AUD-d-2（新，R4b 引入）：命令通道在关中断自旋锁里做可睡眠操作 —— **high**

- 位置：`stealth_hook.c:238-247`（`sh_dispatch` 包住整段 `sh_dispatch_body`）+ `ghost_mem.c:121/128/160/185-208` + `hwbp.c:346/365/383-387/427-433`。
- 影响：`preempt_disable + IRQ off` 下取 `mutex`/`mmap_lock`/`vmalloc(GFP_KERNEL)`/`copy_from_user`。争用时 `schedule()` → `BUG: scheduling while atomic`，且自旋锁不会释放、本地中断保持关闭 → 其它 CPU 在这把锁上自旋到看门狗（默认 10-20s 量级）报 soft/hard lockup → panic/重启。`panic_on_warn=1` 的机器更早炸。
- 定级 **high**：root-only、需命令触发（非 critical）；但「确认可致崩溃」且每次 hook/ghost 命令都要走一遍，不能因「这次没炸」降级。
- 最小修法：见 §2.4(c) 修法 1-2（缩小临界区 + 换真 spinlock_t）。**这是 R4b 新引入的回归，必须在本轮关闭。**

### 3.3 AUD-d-3（新，既有，`47e5b5a` 引入）：`rearm_to` 在调试异常上下文调 perf API，且 rearm 目标未校验 —— **high**

- 位置：`hwbp.c:187-203`，被 `hwbp_handler` 在 `:268`（返回那一拍）与 `:328`（入口捕获后）调用；`hwbp_handler` 自注「调试异常上下文（原子、不可睡眠）」（:205）。
- 事实：`sh_perf_event_disable` / `sh_modify_user_hw_breakpoint` / `sh_perf_event_enable` 三者内部都走 `perf_event_ctx_lock()` → `mutex_lock(&ctx->mutex)`；per-task 事件还可能在 `event->oncpu == smp_processor_id()` 时走 `task_function_call` 自投 IPI。在异常上下文里做这两件事，要么 `might_sleep()` 报警，要么在中断关闭下等自己的 IPI（硬挂）。三个返回值全部未检查（`rearm_to` 无返回值），失败后节点仍以为已 rearm。
- 另外 `rearm_to(matched, STRIP_PAC(regs[30]))` 把**未校验的 LR** 直接装成断点地址：LR 若指向内核/无效地址，`STRIP_PAC` 会把它变成任意用户地址（AUD-d-1 的第 2 条修法）。
- 定级 **high**：这是「命中一次就可能炸」的路径（真机 selftest 命中过且没炸，只能说明 mutex 当时无争用）。`confidence: 中高`（代码路径确定，实害取决于争用）。
- 最小修法：把 rearm 从异常上下文挪走——命中后只记录「待 rearm 的目标」，用 `irq_work`（KP 可解析 `irq_work_queue`）或 `task_work` 在可睡眠上下文执行 `perf_event_disable/modify/enable`；或改为「入口/返回各注册一个固定断点」，运行期完全不 `modify`。

### 3.4 AUD-d-4（新）：`GHOST_LIST` 对 shell 开放且不按 mm/pid 过滤 —— **low**

- 位置：`stealth_hook.h:72` 定义 `SH_CMD_GHOST_LIST=0x3004`，而 `stealth_hook.c:149` 的门只覆盖 `SH_CMD_GHOST_ALLOC..SH_CMD_GHOST_WRITE`；`ghost_mem.c:215-242` 遍历全局 `ghost_list`，拷 `va/size/pid/prot`。
- 影响：uid 2000 可枚举 root 进程建的 ghost 区域地址/大小/权限，属信息泄露；无写原语，不构成提权。
- 最小修法：门内加 `cmd == SH_CMD_GHOST_LIST`，或按 `node->pid == current->pid` 过滤。
