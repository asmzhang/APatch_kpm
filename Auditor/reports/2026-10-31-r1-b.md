## 2. 问题单

### AUD-b-1 stealth_hook — uid 白名单默认含 shell(2000)，shell 可驱动内核级 HWBP/GHOST 原语
- 位置：`modules/KPM/stealth_hook/stealth_hook.c:39`（`sh_allow_uids[SH_ALLOW_MAX] = { 0, 2000 }`）、`stealth_hook.c:219`（特权门）
- 影响：uid 2000（adb shell）默认可通过 syscall 427 对**任意 tid**（无同 uid/同进程校验，`sh_hwbp_hook` 只查 tid 存在）注册硬件断点、dump 该线程寄存器与指针指向内存（`hwbp.c:271-294`），并可 `GHOST_WRITE` 任意可写页。等效 ptrace 级越权读取面，攻击者只需拿到 shell（很多利用链的起点）即可监视/篡改其他进程。
- severity：high（权限面过大，可达跨进程信息泄露/篡改）
- frequency：取决于设备上是否有以 shell 身份运行的不可信代码；无法从静态审计断定
- confidence：high（代码直接可读：特权判断仅 uid 表，无进程归属校验）
- 验证方法与证据：`sh_hwbp_hook`（hwbp.c:308-378）接受任意 `req.target_pid`，特权判断只在 `sh_syscall_before`（stealth_hook.c:219）一层；默认表含 2000。
- 建议修复方向：默认表收紧为 `{0}`；或对非 root 调用者加目标进程 uid 校验（`task->cred->uid == caller uid` 才允许挂断点/写内存）。

### AUD-b-2 stealth_hook — hwbp dump 关 PAN 后裸解引用用户指针，无异常处理，可致内核 panic
- 位置：`modules/KPM/stealth_hook/hwbp.c:281-293`
- 影响：命中断点且 `dump_size>0` 时，`msr pan, #0` 后对 `regs->regs[i]` 逐字节 `*(volatile uint8_t*)(ptr+j)` 直接读用户地址。该代码运行在调试异常（原子、不可睡眠）上下文，无法处理缺页：指针指向已换出/未映射页时发生 data abort → 内核 oops/panic，整机可重启。地址界检查（`ptr<0x100000 || ptr>0x7FFFFFFFFFFF`）既不能保证页在内存，也不能保证指针仍是合法对象（TOCTOU）。
- severity：critical（确认可致内核崩溃；不因频率未知降级）
- frequency：每次带 dump 的命中且寄存器指向无效页时必现；实际触发率取决于被测进程行为
- confidence：high（机制明确：原子上下文 + 关 PAN + 裸解引用）
- 验证方法与证据：hwbp.c:281 `.inst 0xd500409f`（msr pan,#0）、:289 直接解引用、:293 恢复 PAN；上下文为 perf 溢出回调（hwbp.c:192-193 注释自认"原子、不可睡眠"）。
- 建议修复方向：改用 `copy_from_user` 类带 fixup 的安全拷贝（如 `raw_copy_from_user` + `pagefault_disable/enable` 包裹，或 `probe_kernel_read` 语义）；KP 若无对应导出，可 kallsyms 取 `__arch_copy_from_user` 并配 `uaccess` 异常表上下文，仍不可用时宁可不做 dump。

### AUD-b-3 stealth_hook — hwbp_list / ghost_list 全程无锁，原子上下文读与进程上下文写并发
- 位置：`modules/KPM/stealth_hook/hwbp.c:86`、`ghost_mem.c:38`（裸 `struct list_head`）；写点 `hwbp.c:370-373`（插入）、`hwbp.c:388-404`（删除）、`ghost_mem.c:137-140`、`ghost_mem.c:259-266`；读点 `hwbp_handler`（hwbp.c:204-215，调试异常上下文）
- 影响：多线程并发下发 HOOK/UNHOOK/GHOST_ALLOC/FREE，或 handler 触发与命令并发时，链表指针撕裂 → 死循环、UAF、内核内存破坏。
- severity：high（可致内核崩溃/内存破坏）
- frequency：依赖调用方并发模式；单线程 CLI 顺序使用时不触发
- confidence：high（全文件 grep 无 spin_lock/ mutex/ rcu 原语）
- 验证方法与证据：`grep -n 'lock\|spin\|rcu\|atomic' modules/KPM/stealth_hook/*.c` 无命中。
- 建议修复方向：每链表配 `spinlock_t`（handler 是原子上下文，用 `spin_lock_irqsave`；ghost 命令路径可进程上下文但需同锁）；或至少在文档与 CLI 协议里强制串行化并开单跟踪。

### AUD-b-4 stealth_hook — `sh_vmalloc` 等符号解析失败未判空即调用
- 位置：`modules/KPM/stealth_hook/ghost_mem.c:128`（`node = sh_vmalloc(sizeof(*node))` 无判空；仅判了 `sh_vm_mmap`）、`hwbp.c:341`（同）；`sh_hwbp_resolve()`（hwbp.c:133-172）只校验 register/release 符号，不校验 `sh_vmalloc/sh_vfree/sh_copy_from_user/sh_find_task_by_vpid`
- 影响：kallsyms 解析 `vmalloc`/`__arch_copy_from_user` 失败（符号被裁剪的内核）时，`sh_hwbp_hook`/`sh_ghost_alloc` 对 NULL 函数指针调用 → 内核崩溃。`sh_copy_from_user` 在两处都有判空（hwbp.c:322、ghost_mem.c:185），唯独 vmalloc 路径漏了。
- severity：medium-high（崩溃，但触发前提是符号缺失）
- frequency：低（仅符号裁剪内核）
- confidence：high（代码路径直接可见）
- 验证方法与证据：ghost_mem.c:106-110 只判 `sh_vm_mmap`；hwbp.c:166-170 只判 register/release。
- 建议修复方向：`sh_hwbp_resolve`/`sh_ghost_resolve` 把必需符号集（vmalloc、vfree、copy_from_user）纳入存在性校验，任一缺失即整体返回不支持。

### AUD-b-5 stealth_hook — 目标 task_struct 无引用保护，线程退出后 use-after-free
- 位置：`modules/KPM/stealth_hook/hwbp.c:335-359`（`sh_find_task_by_vpid` 返回的 `task` 直接传入 `perf_event_create_kernel_counter`，未 `get_task_struct`）；节点生命周期未跟踪线程退出（`sh_hwbp_unhook`/`sh_hwbp_cleanup` 之外无 per-thread 清理）
- 影响：目标线程在断点注册前/中退出，`task_struct` 释放后仍被使用 → UAF；线程退出时 perf 事件被内核自动释放，模块侧 `node->bp_handle` 悬空，后续 `sh_hwbp_enable/rearm_to` 对悬空句柄调 `perf_event_enable/disable` → 二次 UAF。
- severity：high（UAF 可致崩溃/内存破坏）
- frequency：取决于目标线程生命周期；hook 短命线程时高
- confidence：high（代码可见无引用计数调用；KP 导出表亦无 `get_task_struct`，需 kallsyms 自取）
- 验证方法与证据：hwbp.c:335-359 全程无 `get_task_struct`/`put_task_struct`；perf 内核语义（task 退出自动释放事件）为内核公开行为。
- 建议修复方向：hook 前 `get_task_struct(task)`、`perf_event_create_kernel_counter` 成功后按事件所有权决定释放；并注册 `do_exit`/`release_task` 观察点或周期校验 `pid_alive(task)` 后再操作句柄。

### AUD-b-6 stealth_hook — 模块卸载 `inline_unhook_syscalln` 返回值未检查
- 位置：`modules/KPM/stealth_hook/stealth_hook.c:319`
- 影响：unhook 失败（如 KP 内部状态异常）时模块照常卸载，syscall 427 入口残留指向已卸载代码的跳板 → 卸载后任何 io_uring_register 调用崩溃。
- severity：medium
- frequency：低（仅在 unhook 失败路径）
- confidence：medium-high（未检查返回值是事实；KP 内部失败条件未核实）
- 验证方法与证据：stealth_hook.c:319 无返回值接收；对照 mount_hidder 用 `hook_unwrap_remove(...,1)` 亦未检查返回值（见 AUD-b-9 备注）。
- 建议修复方向：unhook 失败时拒绝卸载（返回错误码）并打日志。

### AUD-b-7 stealth_hook — ctl0 uid 解析整数溢出 + dump 函数 snprintf 返回值误用（模式性越界风险）
- 位置：`modules/KPM/stealth_hook/stealth_hook.c:277-281、286-290`（`uid = uid*10 + digit` 无长度/溢出检查）；`stealth_hook.c:94-104 sh_dump_allow`（`n += kf_snprintf(...)` 累加的是"应写长度"而非实际长度，`out+n` 与 `out_size-n` 可同时越界）
- 影响：ctl0 输入超长数字串溢出成意外 uid（ctl0 通道本身需 superkey，实际攻击面小）；`sh_dump_allow` 在极端长表下指针/size 失配——受 `SH_ALLOW_MAX=8` 与 128 字节 buf 限制，当前参数下不会实际越界，属潜伏模式。
- severity：low
- frequency：低
- confidence：high（模式明确，当前参数下不可达）
- 验证方法与证据：`sh_allow_count` 上限 8、每 uid ≤10 字符、buf 128 → 最大 ~100 字节，安全余量存在但依赖巧合。
- 建议修复方向：uid 解析限定 ≤10 位；`sh_dump_allow` 用 snprintf 实际返回值钳制（`if (r < 0 || r >= left) break; n += r;`）。

### AUD-b-8 mount_hidder — `strnstr` 子串匹配会误伤同名子串路径
- 位置：`modules/KPM/mount_hidder/hide_mount.c:181`
- 影响：添加 `/data/abc` 会把 `/proc/mountinfo` 中含 `/data/abcxyz`、`/data/abcd` 的挂载项一并隐藏；若两应用路径互为前缀子串，隐藏范围超出预期（功能正确性/最小权限问题，非崩溃）。
- severity：low
- frequency：取决于用户配置的路径表；默认三条路径前缀冲突概率低
- confidence：high（strnstr 语义确定；README.md:12 已自认该行为）
- 验证方法与证据：hide_mount.c:181 `strnstr(m->buf + base, hm_paths[i], len)`，无路径边界（`'\n'`/`' '`）锚定。
- 建议修复方向：匹配改为「行内 token 边界匹配」（在 mountinfo 行的 mountpoint 字段位置比较，或要求匹配串后随 `' '`/`'\n'`/行首）。

### AUD-b-9 mount_hidder — ctl0 命令前缀匹配过宽 + unhook 返回值未检查
- 位置：`modules/KPM/mount_hidder/hide_mount.c:254`（`strncmp(args,"status",6)` 使 `statusXXX` 也按 status 处理）、`:259`（`clear` 同理）、`:204`（`hook_unwrap_remove` 返回值未检查）
- 影响：误输入 `statusx` 得到 status 输出、`clearfoo` 清空路径表——行为混淆，无内存安全问题；unhook 返回值未检查意味着卸载期若 KP 内部摘钩失败，模块仍报告正常退出（与 AUD-b-6 同类模式，此模块为 wrap 链，失败后果轻于 syscall 跳板）。
- severity：low
- frequency：低
- confidence：high（语义确定；KP `hook_unwrap_remove` 失败条件未核实——标注为部分未核实）
- 验证方法与证据：hide_mount.c:254-263、:201-205。
- 建议修复方向：命令比较加长度/`\0` 校验；unhook 失败打日志并考虑返回非 0。

## 4. 未覆盖内容（显式列出）

1. **真机行为**：全部结论为静态审计 + 产物字节解析，未做任何设备验证（Tester 职责）。
2. **KP 内部实现细节**：`hook_unwrap_remove`/`inline_unhook_syscalln` 的失败条件与 `__arch_copy_from_user` 异常表语义未深入 KernelPatch 源码逐行核实（只核了导出符号存在性）。
3. **kallsyms 符号在目标内核上的存在性**：`show_vfsmnt`/`perf_event_create_kernel_counter` 等是否在具体设备 kallsyms 中可用，未核实（依赖目标镜像）。
4. **`task_struct_offset.cred_offset`/`cred_offset.uid_offset` 的初始化时机**：KP 在模块加载前是否必然填充未核实；stealth_hook 的 `sh_current_uid()`（stealth_hook.c:42-46）对这两个值无防御，若为 0 会读错位——标注未核实。
5. **上游 xiaojianbang-stealth-hook / 上游 mount_hidder 逐行 diff**：仅按本仓 README/源码注释声明核对关键差异点（如 data0=count+1 的正确性经独立推演确认），未拉取上游仓库比对。
6. **性能影响**：syscall 427 通道对 io_uring_register 正常调用的开销（magic 判断）未测量。
7. **同目录其余模块**（apkey_hide/memcrc/panda_hide/qti_battery_charger/xperia_ii_battery_age）不在本轮范围。
