## 逐条复核

### 1) AUD-e-3 是否真消除

**字面内容确已消除，但 AUD-d-3 的核心问题仍在（拆为 AUD-f-1）。**

- rearm_to（hwbp.c:235-257）异常路径现状：
  - `sh_user_addr_ok(addr)`（hwbp.c:94-97）纯整数比较 ✓
  - 越界置 `is_disabled = 1`（hwbp.c:245）✓
  - `access_remote_vm` / `get_task_mm` / `mmput` 已完全移出该路径 ✓
- **handler 内仍留的可睡眠调用清单**：
  1. `sh_perf_event_disable` / `sh_modify_user_hw_breakpoint` / `sh_perf_event_enable`（hwbp.c:250-256，经 rearm_to）。6.1 内核这三个入口都经 `perf_event_ctx_lock` 走 `mutex_lock(&ctx->mutex)`（modify 还涉及事件迁移路径）。调试异常上下文（IRQ 关闭）里 mutex 争用时睡眠 = scheduling while atomic。与实现方自述 dmesg 计数 2（R4b 遗留）吻合。
  2. hwbp.c:376-377 dump 兜底 `__arch_copy_from_user`，仅在 `sh_copy_from_user_nofault` 缺符号时走到 —— AUD-f-2。
  3. hwbp.c:370-372 `copy_from_user_nofault` 设计为原子安全，风险可忽略。
- **判：可修，非机制固有。** 机制固有的只是「溢出回调发生在原子上下文」；rearm 不必在回调里完成。最小改法（推荐）：`sh_hwbp_node` 增 `pending_rearm_addr`/`pending_rearm` 两字段；rearm_to 只写字段即返回（纯写）；`sh_dispatch`（进程上下文、持 sh_cmd_mutex，stealth_hook.c:265）入口遍历链表 flush pending rearm —— 此时调 perf 三件套合法。零新增 kallsyms 依赖，代价是返回断点晚一拍生效。
- **若接受风险**，触发条件须写清：仅观察者状态机 rearm 路径执行；`ctx->mutex` 无争用时 perf 走快速路径不睡眠；争用（同线程另一 perf 操作）时睡眠。后果：atomic-sleep 告警开启时是可预期 warn，关闭时最坏为异常上下文调度 → 上下文/栈破坏 → panic。按本仓规则（确认可致崩溃不因频率降级）维持 **high**。

### 2) AUD-d-1 残留 —— 关闭

- SKIP_ORIGIN：hwbp.c:298 先 `STRIP_PAC(regs->regs[30])`，hwbp.c:301 `sh_user_addr_ok(lr)` 越界则 `is_disabled=1` 并 return，不写 pc；通过才 `regs->pc = lr`（hwbp.c:306）。✓
- INLINE：入口 hwbp.c:448-449 `sh_addr_is_valid(task, req.trampoline_addr)` 完整校验（可读性，进程上下文）；handler 侧 hwbp.c:321-324 算术兜底。✓
- 回滚干净性：hwbp.c:451-455 `sh_vfree(node)` + 条件 `sh_put_task_struct(task)`，与 hwbp.c:443-446 的 `sh_get_task_struct` 严格配对（缺符号时 task_ref==0，put 被条件挡住，不多放）；节点未入链。更早的 target_addr 校验失败（hwbp.c:429-432）在取引用之前。bp_handle 注册失败路径 hwbp.c:466-476 同样回滚引用与节点。✓
- 残余（不单开单，info）：LR/trampoline 页可在 hook 存续期间被解除映射，handler 只有算术检查，pc 指向未映射用户页的后果是目标进程用户态段错误，非内核提权/panic；属异常上下文物理上无法消除的窗口。

### 3) AUD-e-1 / AUD-e-2 —— 均关闭（e-1 带保留）

- e-1：`sh_cmd_mutex` = `unsigned long[16]` = 128 B（stealth_hook.c:223），注释写明假设。推断依据：arm64 6.1 无 lockdep 时 `struct mutex` ≈ 48 B（count+wait_lock+wait_list+owner+opts）；`DEBUG_MUTEXES` 叠加后 ≈ 104 B < 128。**推断足够。未核实：目标 6.1.99-android14 实际 .config（厂商 config 不在仓库）；LOCKDEP 全开目标需按注释重核。** 建议（非阻塞）：直接用真实 `struct mutex` 声明或把 `sh_cmd_mutex_ready` 移到数组之前加哨兵。
- e-2：`sh_cmd_lock_init` 唯一调用点 `stealth_hook_init`（stealth_hook.c:311），KPM init 在加载路径单线程执行；且先于 `inline_hook_syscalln`（stealth_hook.c:321），命令到达时锁必然已初始化。运行期 `sh_dispatch`（stealth_hook.c:265-267）只 lock/unlock。缺符号降级分支同时清 lock/unlock 两个 fn 指针（stealth_hook.c:238-239），无半初始化。✓

### 4) AUD-b-3 残留 + 未同步窗口

- `sh_hwbp_set_override`（hwbp.c:636-638）、`sh_hwbp_set_skip`（hwbp.c:669-671）均先跳 retired；enable/query 此前已跳（hwbp.c:532-534、571-573）。**关闭。**
- 命令通道串行化：全部命令过 `sh_dispatch` mutex。剩余窗口：
  - handler 原子上下文不可能持 mutex → 命令写（override_mask/override_args/ret_value/flags/skip_count）与 handler 读无共同锁。ARM64 对齐单字段读写原子，多字段组合可撕裂（AUD-f-3）。
  - mutex 符号缺失降级（stealth_hook.c:236-239）时命令通道自身也不串行化（AUD-f-5）。

### 5) 本次改动自身新问题

- AUD-f-3（low，hwbp.c:641-651）：set_override 先置 flags 位（hwbp.c:646-651）后写 args/ret_value 顺序上 args 在前 flags 在后——实际代码先写 override_mask/args/ret_value（641-645）再置 flags 位，顺序已正确；但与 handler 并发时仍是普通写、无屏障，`SKIP_ORIGIN` 位的可见性早于 `ret_value` 写到达 handler 核时，一拍内 ret_value 用旧值。最小修法：维持现有字段顺序即可（已是最优序），如需严格序需 kallsyms 取 `smp_wmb`，成本高于收益，建议登记接受。
- AUD-f-4（info，hwbp.c:283-285）：single_active 兜底——matched 缺失/禁用而链上恰有一个活跃节点时，把该节点当命中者记数并执行其语义；两线程各一节点、其一 disabled 时 B 事件记到 A 节点。上轮已存在，未新增。
- AUD-f-5（low）：降级路径下 `sh_hwbp_hook` 尾插（hwbp.c:479-482）与 handler 并发遍历（hwbp.c:271-282）无互斥，理论上指针撕裂。需三个 mutex 符号同时缺失 + 并发命令，概率极低，不阻塞。
- commit message 所列改动逐项与代码核对一致，无「声称改了但没改」。
